# 工作复盘设计方案

> 文档状态：重新评估完成，可作为下一轮实现依据
>
> 最后更新：2026-08-11
>
> 适用范围：任务完成记录、父任务、子任务、按日期完成评价、每日复盘、当前任务安排

## 1. 结论

本功能的主要目的不是查看“这周安排了多少工作”，而是回看：

```text
最近实际做了什么？
哪些事情形成了结果？
哪些事情被打断、卡住或改变了？
下一段工作应该怎么调整？
```

因此不推荐继续使用“本周概述”。它听起来像一页被动的统计摘要，不能传达用户需要主动回看和总结的动作。

推荐命名：

| 层级 | 文案 | 选择 |
| --- | --- | --- |
| 侧栏入口 | **工作复盘** | 推荐。表达能力目的，不被某个日期范围绑死 |
| 默认页面标题 | **最近 7 天的工作** | 推荐。直接对应“最近干了啥” |
| 可选范围 | 最近 7 天 / 本周 | 第一版可先只做最近 7 天，范围切换作为很小的后续增强 |
| 周期性动作 | 本周复盘 | 可作为页面内的周期标签或未来固定周流程名称 |

如果产品必须只保留一个“本周”入口，则使用“本周复盘”，不要使用“本周概述”。但在当前需求下，“工作复盘”比“本周复盘”更准确，因为用户关注的是最近事实，不是每周汇报仪式。

一句话定义：

> “工作复盘”把最近一段时间已经发生的工作证据、每日记录和未收口事项放在一起，帮助用户形成下一步调整，而不是重新规划一遍任务。

## 2. 现有“本周概览”方案为什么不再合适

当前实现的“本周概览”以 `planned_date` 为主：

```text
当前安排日期
    -> 七日任务数量
    -> 按日期排列的计划任务
    -> 当前任务完成率
```

这套设计适合回答“接下来哪天安排了什么”，不适合回答“最近实际发生了什么”。主要问题有四个：

1. `planned_date` 是会变化的当前计划，不是工作事实；任务改期后，原来的日期无法从它恢复。
2. 七日数量把未完成计划和真实产出放在同一层，容易让用户误把安排量当成工作量。
3. 顶部完成率只反映当前任务状态，不反映临时事务、探索、阻塞和每日复盘里的实际工作。
4. 页面缺少一个“写下结论并决定下一步”的闭环，浏览完任务后仍然要靠记忆总结。

本轮不建议同时保留“本周概览”和“工作复盘”两个入口。它们都聚合日期任务，用户会不知道应该去哪里回看。应把现有 `week` 视图改造成复盘视图，或先隐藏旧的计划式呈现，再按本方案重做页面主体。

## 3. 术语与功能边界

### 3.1 四个概念必须分开

| 概念 | 回答的问题 | 在复盘中的角色 |
| --- | --- | --- |
| 当前安排 | 接下来准备处理什么 | 只作为“未收口”上下文 |
| 任务完成状态 | 这个任务当前是否结束 | 作为近期完成证据之一 |
| 任务级完成评价 | 某天实际推进得怎么样 | 作为按任务、按日期的事实记录 |
| 每日复盘 | 那天整体发生了什么 | 作为最接近真实工作的叙述证据 |

复盘页面不能把“当前安排”直接写成“已完成工作”，也不能把“完成评价”与“任务完成状态”混成一个百分比。

### 3.2 第一版不做的事

- 不做完整周报、对外分享或导出 PDF；
- 不自动生成一段看似准确但用户没有确认的总结；
- 不把所有当前任务按创建时间当成近期工作；
- 不把 `planned_date` 变成历史事实来源；
- 不为每个任务重复展示一整段每日复盘正文；
- 不先引入工时、时间块、外部日历和精确投入时长；
- 不做复杂 AI 归纳。第一版先把证据排好，让用户自己确认结论。

## 4. 数据事实与可信度

当前数据库已经有几类可以用于复盘的数据，但可信度不同。

| 数据源 | 能说明什么 | 不能说明什么 | 第一版用法 |
| --- | --- | --- | --- |
| `todos.completed_at` | 当前任务最近一次完成时间 | 任务被重新打开后会清空；删除任务后不可见；不是事件历史 | 展示“完成记录”并标注为当前任务数据 |
| `todo_completion_reviews` | 某任务某天的达成结果、实际推进文字和目标快照 | 没有评价的任务不代表没有工作 | 作为按日工作证据，优先级高 |
| `daily_reviews` | 用户对整天工作的主动叙述 | 不能自动拆成任务、工时或产出数量 | 作为每日时间线的主叙述 |
| `planned_date` | 任务当前安排在哪天 | 不能证明那天真的做过；改期会覆盖过去安排 | 只放在“还没收口”区 |
| `created_at` | 任务何时进入系统 | 不能证明何时开始工作 | 不作为工作量指标 |

因此页面文案使用“工作记录”“完成记录”“有记录的工作日”，不使用“完整产出”“真实工时”或“本周所有工作”。

### 4.1 第一版的历史口径

第一版可以提供有价值的“证据型复盘”，但必须接受以下限制：

- 已完成且仍保留 `completed_at` 的任务可以显示；
- 已重新打开的任务可能没有历史完成记录；
- 已删除任务不会出现在复盘中；
- 每日复盘和任务级完成评价只要保存就会保留，即使任务后来改期；
- 没有任何记录的日期显示“没有留下复盘记录”，不能推断为“那天没有工作”。

如果上线后用户明确需要不可丢失的历史产出，再增加活动事件表；本方案不偷偷把当前字段包装成历史审计系统。

## 5. 时间范围

### 5.1 默认范围：最近 7 个本地日历日

默认范围为“今天及之前连续 6 天”，而不是当前周一到周日：

```js
function getRecentReviewRange(baseDate = new Date()) {
  const endDate = getRelativeLocalDate(0, baseDate);
  const startDate = getRelativeLocalDate(-6, baseDate);
  return {
    startDate,
    endDate,
    startKey: getLocalDateKey(startDate),
    endKey: getLocalDateKey(endDate),
  };
}
```

选择最近 7 天的原因：

- 周一打开时不会只剩“今天”一个有效日期；
- 周末与周一之间不会因为自然周切换而丢掉最近发生的工作；
- 与用户的“最近干了啥”措辞一致；
- 可以覆盖上一个周末和本周初的连续工作事实；
- 不需要用户理解“当前周是否已经结束”。

### 5.2 范围显示和未来扩展

页面顶部明确显示日期范围，例如：

```text
工作复盘
最近 7 天 · 8月5日 - 8月11日
```

第二阶段可增加轻量范围切换：

```text
最近 7 天      本周      上一段 7 天
```

第一版不提供任意日期筛选、月历和无限向前翻页。复盘入口的职责是快速回看最近工作，不变成历史档案管理器。

### 5.3 当前日期与未来任务

- 只显示今天及过去日期；
- 当前计划在未来的任务不进入“实际发生”时间线；
- 未来安排可以在“还没收口”区作为下一步上下文显示，但不计入已做工作；
- 今天的任务允许显示当前已完成记录和今日复盘，未完成部分明确标识“仍在进行”。

## 6. 信息架构

页面不再以七日负荷条作为视觉主体，而采用“证据时间线 + 未收口 + 复盘结论”的结构：

```text
工作复盘
最近 7 天 · 8月5日 - 8月11日

有记录的工作日 4       完成记录 6       未收口 3

实际发生
┌─ 8月11日 · 今天 ────────────────────────┐
│ 今日复盘：处理登录问题，确认排序结构是前置工作… │
│ 完成记录：补上登录状态同步                  │
│ 任务评价：接口联调 · 部分达成               │
└────────────────────────────────────────┘
┌─ 8月10日 · 星期一 ───────────────────────┐
│ 今日复盘：完成移动端 390px 布局……           │
│ 完成记录：移动端布局检查                     │
└────────────────────────────────────────┘

还没收口 · 3
□ 430px 操作按钮溢出修复       原安排 8月10日
□ 接口联调结果                 部分达成

复盘结论
[这段时间最重要的产出、反复出现的阻塞、下一段调整……]
```

### 6.1 页面头部

标题和摘要直接说明事实口径：

```text
TODOLIST · 工作记录
工作复盘
最近 7 天 · 4 个工作日留下记录 · 6 条完成记录
```

不显示“当前完成率”圆环作为主指标。复盘页面的首要问题是“发生了什么”，不是“完成率多少”。原有圆环可以隐藏，或降为“任务状态”辅助信息，但不应占据页面第一视觉。

### 6.2 事实时间线

时间线按日期倒序排列，最近一天在上方。每个日期组只在有证据时出现：

1. 每日复盘正文摘要；
2. 当日 `completed_at` 对应的完成记录；
3. 当日 `todo_completion_reviews` 的任务评价；
4. 当日没有日级正文但有任务证据时，显示“这一天没有写每日复盘”；
5. 当日完全没有记录时不创建空日期组。

日期组的主语是“实际发生”，不是“当天安排”。如果任务的当前 `planned_date` 已经改变，仍按 `completed_at` 或评价日期放回事实发生的日期。

### 6.3 每日复盘正文的显示

- 正文最多显示 3 行摘要，点击后进入现有每日复盘编辑面板；
- 今日日期显示“编辑今日复盘”；
- 历史日期显示“查看这天的复盘”；
- 不自动拼接多个日记段落，不修改用户原文；
- 没有正文但有任务证据时，使用中性文案“有任务记录，尚未写日级复盘”；
- 没有证据时不显示“无工作”，只显示在范围的覆盖统计中。

### 6.4 任务级证据

任务级证据卡片使用现有任务卡片的紧凑变体，但只保留与复盘相关的内容：

- 任务名称；
- `完成于 8月10日` 或评价日期；
- 完成评价结果与实际完成情况；
- 父任务/子任务关系；
- 打开原任务的入口。

不在时间线中显示未来完成目标、日期菜单、分组拖拽等计划操作，避免复盘页面退化为第二个待办列表。原任务的完整编辑和改期仍回到任务工作区。

### 6.5 “还没收口”区

它是复盘的反向证据，不是另一份计划清单。纳入规则：

- 当前未完成，且 `planned_date` 在复盘范围内或已经逾期；
- 或在范围内有 `partial / missed` 评价，当前仍未完成；
- 未来安排但没有范围内历史证据的任务不自动塞入，避免区块变成后续待办。

每条显示：

```text
任务名 · 未完成 / 部分达成 / 未推进
原安排日期（如果仍有）
最近一次评价摘要（如果有）
继续处理 / 打开任务
```

最多默认显示 5 条，超过后折叠。顺序为：有“未推进/部分达成”评价的任务优先，其次是已过期未完成任务，最后按最近评价日期和当前安排日期排序。

### 6.6 复盘结论

复盘必须允许用户留下最终判断，但不能强迫用户每次填写长报告。

第一版建议提供一个可选的短文本框，提示语为：

```text
这段时间最重要的产出是什么？
哪些阻塞或计划外工作值得记住？
下一段工作准备保留、停止或调整什么？
```

产品层面称为“复盘结论”，不称为“周报”。保存后按当前范围关联，不影响任务状态。正文上限建议 3000 字符，与 `daily_reviews` 保持一致。

## 7. 命名方案对比

| 名称 | 用户第一反应 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| 本周概述 | 看一个摘要 | 中性、成本低 | 没有回顾动作，不说明事实还是计划 | 不采用 |
| 本周总结 | 看一份结果报告 | 易理解 | 暗示已经完成、偏对外汇报 | 不采用 |
| 本周复盘 | 回看并思考本周 | 目的明确、符合周节奏 | 固定自然周，周一内容偏少 | 仅在固定周流程时采用 |
| 工作回顾 | 回看工作 | 语气自然 | “回顾”缺少调整下一步的意味 | 可用于副标题 |
| **工作复盘** | 回看工作并找出调整 | 目的明确、可扩展到任意时间窗 | 需要页面明确显示日期范围 | 推荐 |
| 最近做了什么 | 看最近做过的事情 | 口语、直白 | 不能覆盖阻塞与下一步 | 可作为空状态文案 |

最终文案建议：

```text
侧栏：工作复盘
页面：工作复盘
范围：最近 7 天 · 8月5日 - 8月11日
主区：实际发生
次区：还没收口
结尾：复盘结论
```

## 8. 方案与数据实现

### 8.1 复盘派生数据

建议增加独立的派生函数，不修改 `getLaterEntries()` 的含义：

```js
function getRecentReviewRange(baseDate = new Date()) {}
function getRecentReviewEntries(range) {}
function getCompletedEntriesForDate(entries, dateKey) {}
function getCompletionReviewsForDate(dateKey) {}
function getDailyReviewEvidence(dateKey) {}
function getOpenReviewItems(range) {}
```

所有查询都先把 `YYYY-MM-DD` 转成本地日期键，再做字符串范围比较，沿用当前项目避免 UTC 偏移的策略。

### 8.2 事实分类规则

```text
实际发生：
  completed_at 的本地日期在范围内
  或存在 review_date 在范围内的任务级完成评价
  或存在 review_date 在范围内的每日复盘

还没收口：
  当前未完成
  且当前安排日期在范围内或早于今天
  或范围内存在 partial / missed 评价
```

同一个任务可能同时出现在“实际发生”和“还没收口”：

```text
完成了接口设计，但接口联调仍为部分达成
```

这不是重复，而是复盘需要同时看到产出与剩余工作。UI 中应使用两个明确区块，不能只依赖颜色区分。

### 8.3 完成记录去重

父任务和子任务可能在同一天同时完成，父任务也可能因为所有子任务完成而自动完成。第一版处理方式：

- 原始计数保留父任务与子任务两个实体，便于核对任务状态；
- 时间线视觉上默认显示父任务，并把同日完成的子任务收进“完成的子任务 N 项”；
- 如果父任务没有完成但子任务完成，则直接显示子任务记录；
- 摘要文案使用“完成记录”，不使用“完成任务数量”，避免把父子层级重复包装成产出数量。

### 8.4 复盘结论的持久化选择

复盘结论如果只保存在浏览器本地，会在换设备、清理缓存或账号切换后丢失，不符合复盘的长期价值。

建议第二阶段增加一张轻量表：

```sql
create table if not exists public.work_reviews (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  range_start date not null,
  range_end date not null,
  content text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint work_reviews_range_check check (range_start <= range_end),
  constraint work_reviews_content_check check (length(trim(content)) between 1 and 3000),
  constraint work_reviews_one_per_range unique (user_id, range_start, range_end)
);
```

第一阶段也可以先只实现事实时间线，待用户确认“确实会在这里写结论”后再增加表和 Realtime。不要为尚未验证的每周仪式提前增加数据库负担。

### 8.5 历史事件的后续数据模型

如果需要“完整、不可被当前任务状态覆盖的工作历史”，新增事件表，而不是继续扩展 `planned_date`：

```sql
todo_activity_events (
  id,
  user_id,
  todo_id,
  event_type,
  event_at,
  payload jsonb
)
```

首批事件可包含：`completed`、`reopened`、`planned`、`unplanned`、`deleted`。事件由客户端操作和数据库触发器共同保证，避免删除任务后所有历史一起消失。

这属于第二阶段，因为它涉及事件语义、幂等、历史迁移和删除触发器，不能为了一个 UI 页面草率添加。

## 8.6 同类产品调研

本轮调研只借鉴“复盘的结构”，不照搬付费产品的工作流或时间管理模型。

### Todoist Upcoming：计划浏览不是复盘

Todoist 的 Upcoming 面向未来任务安排和日期浏览，适合回答“接下来有什么”。这验证了原“本周概览”方案的定位：它是计划预览，而不是事实回顾。复盘页面应把 Upcoming 类的计划信息降为“还没收口”上下文，不能继续把未来任务放在主视觉。

参考：[使用预览视图计划您的一周](https://www.todoist.com/zh-CN/help/articles/plan-your-week-with-the-upcoming-view-OKOg1mR8)、[Use the calendar layout in Todoist](https://www.todoist.com/help/articles/use-the-calendar-layout-in-todoist-lPHRQTu0o)

### Sunsama Weekly Review：复盘需要事实、结论和下一步

Sunsama 将 Weekly Review 与 Weekly Objectives、Weekly Planning 分开。Weekly Review 的价值不只是列出完成项，而是回看目标进展、已完成工作和下一步调整。这支持本方案把页面结构拆成“实际发生”“还没收口”“复盘结论”三层，而不再继续扩展七日负荷统计。

参考：[Weekly Review](https://help.sunsama.com/docs/usage-guides/weekly-objectives/weekly-review/)、[Weekly Planning](https://help.sunsama.com/docs/usage-guides/weekly-objectives/weekly-planning)

### Microsoft To Do Planned：统一计划入口仍不等于工作历史

Microsoft To Do 的 Planned 智能列表将设置了日期的任务集中展示，说明日期任务确实需要统一入口；但它依然是计划聚合。对本项目而言，`planned_date` 只能放在“还没收口”区，不能单独代表已经做过的工作。

参考：[Add due dates and reminders in Microsoft To Do](https://support.microsoft.com/en-us/office/add-due-dates-and-reminders-in-microsoft-to-do-064d9696-08d1-4433-bfdd-f661dc97491f)

### 调研结论

```text
Upcoming / Planned：未来安排
Daily Review：当天发生了什么
Weekly Review：从事实中得出什么结论、下一步怎么调整
```

本项目已有每日复盘和任务级每日完成评价，因此最有价值的增量不是再做一个计划列表，而是把这些已有事实组织成一个可回看的工作复盘入口。

## 9. 视觉与交互方向

本页的主题不是“未来工作刻度”，而是“桌面上的工作证据”。沿用现有深色工作台、Noto Serif SC 标题、Inter 正文和等宽日期标记；只把一个视觉重点从七日负荷条移到逆时间时间线。

### 9.1 页面结构

```text
标题与日期范围
────────────────────────────
轻量事实摘要
────────────────────────────
实际发生（逆时间）
  日期标记 ── 复盘正文 / 完成记录 / 任务评价
  日期标记 ── 复盘正文 / 完成记录
────────────────────────────
还没收口
────────────────────────────
复盘结论
```

### 9.2 设计令牌

| 语义 | 现有令牌 | 用途 |
| --- | --- | --- |
| 事实时间线 | `--neon-blue` | 时间线连接线、证据标签 |
| 已完成记录 | `--neon-green` | 明确结果已产生 |
| 部分达成/待调整 | `--neon-orange` | 需要思考但不是错误 |
| 未推进/逾期未收口 | `--neon-pink` | 需要处理的偏差 |
| 日级正文 | `--text` / `--text-dim` | 保留叙述优先级 |

不增加指标卡、七列柱状图和大面积渐变。页面唯一的识别特征是“日期标记 + 证据叠层”的时间线。

### 9.3 移动端

- 时间线改为单列，日期标记缩短为 `8月11日 · 今天`；
- 完成记录和每日复盘正文纵向堆叠，不做左右两栏；
- “还没收口”默认只显示 3 条，点击后展开；
- 复盘结论输入框保持完整宽度，保存按钮固定在面板底部；
- 320px 宽度下不出现横向任务卡片滚动区；
- 不用颜色作为唯一状态提示，所有结果同时显示文字。

## 10. 交互流程

### 10.1 打开复盘

1. 用户点击侧栏“工作复盘”；
2. 页面显示最近 7 天范围并立即加载已有证据；
3. 默认滚动位置在最近日期，不展开未来计划；
4. 如果今天没有任何记录，顶部显示“今天还没有留下记录”，但不判定今天没有工作。

### 10.2 从证据回到任务

- 点击完成记录进入原任务所在分组，并定位到任务卡片；
- 点击任务评价打开现有评价面板，日期保持原评价日期；
- 点击当前未收口项进入原任务并保持任务当前安排；
- 返回复盘时重新计算当前数据，不缓存过时的统计。

### 10.3 写复盘结论

- 结论是可选操作，不阻塞离开页面；
- 保存时保留当前范围的开始和结束日期；
- 范围改变后，旧结论仍属于旧范围，不被覆盖；
- 删除结论需要确认；
- 保存失败保留正文并显示明确错误。

## 11. 空状态与错误状态

### 11.1 完全没有证据

```text
最近 7 天还没有留下可回看的记录
先从今日复盘写下一两句，之后这里会按日期形成工作轨迹。
```

这里不能写“最近 7 天没有工作”，因为系统没有足够事实证明这一点。

### 11.2 只有计划没有事实

```text
这段时间有 3 项安排，但还没有完成记录或复盘正文
计划不等于产出；可以先补写每日复盘，或回到任务填写完成评价。
```

### 11.3 数据加载失败

保留当前工作台的云端错误提示，并允许重试。不要用 0 条记录替代加载失败，避免让用户误以为历史被清空。

## 12. 实施阶段

### 阶段一：把现有周视图改成复盘信息架构

1. 将侧栏文案从“本周概览”改为“工作复盘”；
2. 将 `week` 的固定自然周派生改为最近 7 天事实范围；
3. 移除七日负荷条和当前完成率主指标；
4. 增加逆时间事实时间线；
5. 聚合 `daily_reviews`、`todo_completion_reviews` 和 `completed_at`；
6. 增加“还没收口”区，保留跳回原任务的入口；
7. 明确所有统计使用“记录”口径。

### 阶段二：复盘结论与范围切换

1. 增加可选复盘结论输入；
2. 增加 `work_reviews` 表、RLS、索引和 Realtime；
3. 增加“最近 7 天 / 本周”切换；
4. 保存每个范围独立的结论，不覆盖其他范围；
5. 增加上一段范围导航前的使用频率验证。

### 阶段三：可信历史

只有在用户确实需要“完整回看过去做过什么”时才做：

1. 设计 `todo_activity_events` 的事件语义；
2. 为完成、重新打开、改期、取消安排和删除记录事件；
3. 处理已有 `completed_at`、评价和每日复盘的迁移/兼容；
4. 将复盘页面的事实来源从当前任务快照逐步切换到事件流。

## 13. 验收标准

### 13.1 目标与命名

- 侧栏和页面使用“工作复盘”，不再把页面称为“本周概览”；
- 页面标题明确展示“最近 7 天”和具体日期范围；
- 页面第一视觉是实际发生的工作记录，不是未来任务量；
- 页面不暗示自己是完整历史审计或对外周报。

### 13.2 事实聚合

- `completed_at` 在范围内的任务进入对应实际完成日期；
- 任务级完成评价按 `review_date` 进入对应日期；
- 每日复盘按 `review_date` 进入对应日期，并保留原文摘要；
- 当前安排日期改变后，历史评价和每日复盘不会消失；
- 当前未完成且范围内有安排/评价的任务进入“还没收口”；
- 未来安排不会被误当成已完成工作；
- 父任务与子任务不在摘要中被包装成不透明的“产出数量”。

### 13.3 交互

- 可从时间线打开对应每日复盘或任务评价；
- 可从完成记录定位回原任务；
- 未收口任务可返回当前任务工作区继续处理；
- 没有证据的日期不显示为空任务组；
- 复盘结论是可选的，保存失败不丢正文；
- 改变范围后，结论不会覆盖其他范围。

### 13.4 响应式与可访问性

- 320px、390px、768px 和桌面宽度下无横向溢出；
- 时间线状态同时有文字和结构提示，不依赖颜色；
- 日期组使用标题元素，证据项有明确按钮名称；
- 键盘可从日期、证据、未收口项进入对应动作；
- `prefers-reduced-motion` 下不强制平滑滚动或长动画；
- 读屏能区分“完成记录”“任务评价”“每日复盘”和“还没收口”。

## 14. 最终建议

本轮应把产品问题定义为“工作复盘”，而不是“本周工作预览”。

最小可行版本不是再做一张周计划表，而是：

```text
最近 7 天
  -> 按日期回看每日复盘
  -> 叠加完成记录和任务级完成评价
  -> 单独列出还没收口的工作
  -> 最后允许写一段复盘结论
```

这样既能满足“最近干了啥”，又尊重现有数据的真实能力。先用已有记录形成可信的工作轨迹，再根据使用情况决定是否投入周结论存储和完整活动事件。
