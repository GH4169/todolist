# 本周工作概览设计方案

> 历史方案：本文件已被 [工作复盘设计方案](./recent-work-review-design.md) 取代。当前需求的主目标是回看最近实际发生的工作，不再以本周计划快照为主。

> 文档状态：合理性评估与方案调研已完成，可作为后续实现依据
>
> 最后更新：2026-08-11
>
> 适用范围：父任务、子任务、今日待办、明日待办、后续待办、完成目标、每日完成评价

## 1. 结论

建议实现，但第一版应收敛为“本周概览”，而不是完整周历、周目标或周复盘。

推荐方案：

1. 在侧栏“明日待办”和“后续待办”之间增加“本周概览”；
2. 固定展示当前自然周（周一至周日），不提供跨周翻页；
3. 顶部用紧凑的七日概览条展示每天的任务量，详情继续使用按日期分组的纵向任务列表；
4. 聚合父任务和子任务当前的 `planned_date`，复用现有任务卡片、完成目标、完成评价和日期调整操作；
5. 侧栏计数、顶部摘要和完成率都表示“当前仍安排在本周的任务快照”，不宣称是不可变的历史周报；
6. 第一版不新增表、字段或数据库迁移，不创建“周目标”“周总结”数据；
7. 如果后续验证出稳定的周复盘需求，再单独设计基于历史事实的周报，而不是从可变的 `planned_date` 反推历史。

一句话定义：

> “本周概览”帮助用户一次看清当前这一周每天安排了什么、哪里过载、还有多少工作待处理，并能直接调整安排。

## 2. 为什么值得增加

### 2.1 现有导航能执行，但不便于整体判断

当前日期导航将任务分成三个互斥区域：

| 入口 | 范围 |
| --- | --- |
| 今日待办 | `planned_date = 今天` |
| 明日待办 | `planned_date = 明天` |
| 后续待办 | `planned_date > 明天` |

这套结构适合回答“我现在做什么”和“未来还有什么”，但用户需要在多个入口之间切换，才能回答以下问题：

- 本周一共安排了多少工作？
- 周四是否过载，周五是否还有空档？
- 哪些任务已经逾期但仍留在本周？
- 今天完成后，本周剩余工作如何分布？
- 父任务和子任务是否被安排在冲突的日期？

“后续待办”虽然已经按日期分组，但它同时包含本周、下周和更远日期，也排除了今天与明天，不能稳定承担本周总览。

### 2.2 现有数据已经足够支撑第一版

当前系统已经具备：

- 父任务和子任务统一的 `planned_date date`；
- 按日期保存的完成目标；
- 按日期保存的完成评价；
- 任务完成状态和 `completed_at`；
- 获取全部父子任务的 `getTaskEntries()`；
- 日期分组、日期标题和日期视图紧凑卡片；
- 任务与分组的 Realtime 同步。

因此第一版是一个新的派生视图，不需要扩张持久化模型。主要成本集中在周范围计算、导航状态、概览条和分组渲染。

### 2.3 它与“后续待办”互补，而不是替代关系

```text
今日待办：执行今天
明日待办：提前准备明天
本周概览：检查当前周的分布与负荷
后续待办：管理本周之后的长期安排
```

保留四个入口会有日期范围重叠，但它们回答的问题不同。“本周概览”是总览入口，不应为了追求集合互斥而删掉高频的今日和明日入口。

## 3. 关键数据限制

这是本方案最重要的边界。

### 3.1 `planned_date` 是当前计划，不是历史事件

任务从周二改到周四时，数据库只保留周四；用户从日期视图“收起已完成”时，任务的 `planned_date` 会被清空。因此本周概览只能可靠表达：

> 此刻仍然安排在本周的任务情况。

它不能可靠回答：

- 周二当时原本安排了什么；
- 本周曾经改期多少次；
- 已经收起的完成任务原计划在哪一天；
- 某个任务在一周内实际投入了几天；
- 本周真实产出和计划偏差是多少。

界面和文案不得把当前快照包装成“本周报告”“历史完成率”或“周复盘”。

### 3.2 一个任务当前只能出现在一天

每条父任务或子任务只有一个 `planned_date`。即使同一任务保存了多天完成目标，第一版也不能据此把任务复制到多个日期，因为目标不等于当前安排。

父任务和子任务仍是独立计划实体：

- 父任务安排在周三、子任务安排在周四时，两者分别出现；
- 只安排子任务时，不自动补出父任务；
- 不根据子任务日期推断父任务的周跨度；
- 不根据多条目标记录生成虚构的多日任务实例。

### 3.3 完成评价只作为卡片上下文，不补造周历史

当任务仍安排在某个本周日期时，卡片可以显示该日期已有的完成评价。任务改期或清除安排后，不应仅因为该日期存在评价，就把任务重新插入本周计划列表。

原因是本视图的主语是“当前计划”。如果同时混入已移走的历史评价，同一任务可能在过去日期和未来日期重复出现，用户会无法判断哪一条仍需执行。

## 4. 同类产品调研

调研只提取与本项目有关的产品模式，不复制竞品的付费能力、时间管理模型或复杂日历。

### 4.1 Microsoft To Do：日期聚合需要稳定入口

Microsoft To Do 会把设置了日期的任务自动放入 Planned 智能列表，并在同一入口中查看今天、明天及更远日期的任务。

可借鉴之处：

- 日期字段需要一个跨列表的统一聚合入口；
- 今天、明天等高频入口可以与更大范围的计划入口并存；
- 聚合视图应由任务日期派生，不需要创建任务副本。

不直接照搬之处：

- Microsoft To Do 的字段是截止日期，本项目的 `planned_date` 是准备处理日期；
- 本项目不在本功能中增加提醒、重复规则和截止期限。

### 4.2 Todoist Upcoming：周总览必须支持负荷检查和改期

Todoist 将 Upcoming 定义为一周的鸟瞰视图，同时允许在同一处组织未来任务；列表、看板和日历布局都保留日期导航及重新安排能力。其日期选择器还通过每日任务量帮助用户分散工作负荷。

可借鉴之处：

- 周总览不应只是只读统计，发现过载后要能直接调整任务日期；
- 七日选择器或概览条能帮助用户快速比较每天负荷；
- 详情可以继续按日期纵向排列，不必一开始就建设完整周历；
- 逾期任务需要在计划流程中保持可见。

不直接照搬之处：

- 本项目没有任务时刻、持续时长和外部日历事件，七列时间网格会产生虚假的精度；
- 第一版不提供其他周翻页、拖拽跨日、月历、时间块或两年范围浏览；
- 移动端保持纵向日程，不压缩成信息密度过高的七列任务卡片。

### 4.3 Sunsama：周计划、周目标和周复盘是不同层级

Sunsama 将 Weekly Objectives、Weekly Planning 和 Weekly Review 设计为不同流程：周目标用于少量优先事项，具体任务留给每日计划；周复盘则回顾目标进度、完成工作、时间分配和文字反思。

可借鉴之处：

- “查看本周任务”不等于“设定周目标”；
- 面向未来的计划与面向过去的复盘应明确分离；
- 周目标应该少而聚焦，不能直接把所有本周任务当成目标；
- 周复盘需要稳定的历史事实，不能只依赖会变化的当前安排日期。

本项目第一版暂不增加这三种新仪式。现有完成目标是“任务在某一天推进到哪里”，不能自动升级为周目标；现有今日复盘也不自动拼接为周总结。

### 4.4 调研结论

同类产品共同验证了三件事：

```text
日期任务需要统一聚合
    +
周总览需要快速比较每日负荷
    +
计划、目标、复盘不能混为同一个概念
```

对本项目最合适的实现不是完整周历，而是“七日负荷概览 + 按日期分组的任务列表 + 原地改期”。

## 5. 产品定义与范围

### 5.1 用户概念与命名

侧栏和页面标题统一使用“本周概览”。

不推荐：

| 名称 | 不采用原因 |
| --- | --- |
| 本周待办 | 容易被理解为只看未完成，弱化已完成状态 |
| 周计划 | 容易被理解为需要单独填写一份计划 |
| 周报 | 暗示稳定历史、总结和对外汇报 |
| 周复盘 | 暗示面向过去的反思流程 |
| 周日历 | 第一版不是带时刻和持续时长的日历网格 |

### 5.2 第一版支持范围

- 当前本地自然周，周一 00:00 至周日 23:59 的日历日期；
- 父任务和子任务的当前安排；
- 七日任务量比较；
- 按日期分组查看进行中和已完成任务；
- 查看卡片上的当日完成目标和已有完成评价；
- 完成、重新打开、修改内容、调整日期和取消安排；
- 从本周概览创建任务并选择本周内的今天或未来日期；
- 现有 Realtime 同步和账号级视图记忆。

### 5.3 第一版不支持范围

- 查看上周或下周；
- 自定义一周起始日；
- 只看工作日或接入节假日；
- 周目标、周计划正文、周复盘正文；
- 稳定的历史周完成率或计划偏差；
- 多日任务、任务持续天数和时间块；
- 外部日历事件；
- 七列周历、月历或跨日拖拽；
- 按分组、评价结果或完成目标筛选；
- 从每日复盘自动生成周总结；
- 从完成目标或完成评价自动生成任务实例。

## 6. 日期与聚合规则

### 6.1 当前周范围

第一版固定周一为一周起点，周日为终点，符合当前中文界面的默认认知。

日期计算使用本地日历日，并继续采用本地中午构造 `Date` 的现有策略，避免夏令时切换或 UTC 转换导致偏移一天。

```js
function getCurrentWeekRange(baseDate = new Date()) {
  const mondayOffset = (baseDate.getDay() + 6) % 7;
  const startDate = getRelativeLocalDate(-mondayOffset, baseDate);
  const endDate = getRelativeLocalDate(6 - mondayOffset, baseDate);
  return {
    startDate,
    endDate,
    startKey: getLocalDateKey(startDate),
    endKey: getLocalDateKey(endDate),
  };
}
```

必须覆盖跨月、跨年和设备本地日期跨日后的重新计算。

### 6.2 纳入规则

一个父任务或子任务满足以下条件时进入本周概览：

```text
weekStart <= item.plannedDate <= weekEnd
```

规则补充：

- `plannedDate = null` 不显示；
- 进行中和已完成都纳入；
- 父任务和子任务分别计算；
- 已逾期但日期仍在本周的任务保留在原日期组；
- 日期在本周之前的往日未完成不进入本周概览，继续由今日视图的“往日未完成”承接；
- 日期在下周及以后不显示，继续由后续待办承接；
- 改期到本周外后立即从本视图消失；
- 清除安排后立即从本视图消失。

### 6.3 排序规则

1. 日期按 `plannedDate` 升序；
2. 同一天内沿用 `compareTodoOrder`；
3. 进行中与已完成使用现有两个列表；
4. 已完成区默认折叠，并在展开后继续按日期分组；
5. 不增加周视图专属的手动排序，避免与分组内顺序形成两套事实。

### 6.4 计数与完成率口径

| 位置 | 口径 |
| --- | --- |
| 侧栏“本周概览”数字 | 本周内未完成的父任务和子任务数量 |
| 页面摘要“待处理” | 同上 |
| 页面摘要“已完成” | 当前仍保留本周 `planned_date` 且 `done = true` 的数量 |
| 七日概览条 | 每天当前安排的进行中数与已完成数 |
| 顶部完成率 | `本周已完成 / 本周当前安排总数` |

分母为零时显示 `0%`。用户清除已完成任务的安排日期后，完成数和完成率会变化，这是当前快照语义的自然结果。

不使用完成评价的 `achieved / partial / missed` 计算顶部完成率。评价表示某个日期目标的达成结果，任务 `done` 表示整个任务是否完成，两者不能混算。

### 6.5 完成目标与完成评价投影

每张卡片以自身的 `plannedDate` 作为日期上下文：

- 优先显示同日期完成目标；
- 同日期没有目标时，可以沿用现有“上次目标”投影规则；
- 日期为今天或过去且存在同日完成评价时，显示现有评价块；
- 未来日期不允许提前评价；
- 不在周顶部汇总目标文字或评价结果。

这样可以复用现有卡片语义，又不会让七日概览条变成信息过载的报表。

## 7. 信息架构与交互

### 7.1 侧栏入口

```text
今日待办       3
明日待办       2
本周概览       8
后续待办      12
```

“本周概览”放在明日和后续之间，因为它的时间尺度介于两者之间。数字只统计未完成项，与现有三个日期导航保持一致。

图标使用简洁的周历符号；激活色应使用现有中性强调色或绿色，不再增加一套高饱和主题色。按钮结构、焦点态和移动端抽屉行为复用 `.group-nav-item`。

### 7.2 页面头部

```text
TODOLIST · 8月10日 - 8月16日
本周概览
8 项待处理 · 3 项已完成 · 安排在 5 天

                              27%
                            当前完成率
```

环形指标可以复用，但辅助文案建议从通用“完成率”改为“当前完成率”，降低历史报告暗示。其他视图仍保留原文案。

### 7.3 七日概览条

桌面端使用七个等宽单元，移动端仍保持七日横排；每格只放日期、星期和数量，不放任务卡片。

```text
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ 周一 │ 周二 │ 周三 │ 周四 │ 周五 │ 周六 │ 周日 │
│ 8/10 │ 8/11 │ 8/12 │ 8/13 │ 8/14 │ 8/15 │ 8/16 │
│  1   │ 2+1✓ │  0   │  4   │  1   │  0   │  2   │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┘
```

状态规则：

- 今天使用现有今日强调色和 `aria-current="date"`；
- 过去日期弱化，但逾期未完成数使用警示色；
- 未来日期保持正常；
- 空日期显示 `0`，让用户能看见可用空档；
- 数量使用“进行中 + 已完成”简写，不能只显示总数掩盖完成状态；
- 单元格是跳转按钮，点击后滚动到对应日期组；
- 空日期点击后将下方新任务日期切换到该日；过去空日期不可创建任务，只移动焦点到概览说明。

七日条使用稳定高度和网格列宽，数量变化不能造成页面位移。移动端如果 320px 宽度下无法完整容纳星期、日期和双计数，则星期缩写为“一”到“日”，不得缩放字体随视口变化。

#### 视觉方向：一周工作刻度

本视图面向每天反复扫描、安排和执行个人工作的用户，页面唯一任务是让人快速判断这一周的工作分布，并立刻进入需要调整的那一天。

视觉方向沿用当前安静、紧凑的工作台，但把七日概览做成一条连续的“工作刻度”，而不是七张彼此漂浮的卡片：

```text
页面标题与摘要
────────────────────────────────────────
 一      二      三      四      五      六      日
 8/10   8/11   8/12   8/13   8/14   8/15   8/16
  1     2+1✓     0      4      1      0      2
              连续基线 / 今天刻线
────────────────────────────────────────
按日期排列的任务
```

默认深色主题下的设计令牌示意：

| 角色 | 令牌与基准色 | 用途 |
| --- | --- | --- |
| 工作台底色 | `--bg-dark` / `#0b0c0e` | 页面背景 |
| 主文字 | `--text` / `#f4f4f5` | 日期和主要计数 |
| 次要文字 | `--side-muted` / `#858d9c` | 星期和完成数 |
| 今天 | `--neon-orange` / `#fbbf24` | 今天刻线与 `aria-current` 可视态 |
| 完成 | `--neon-green` / `#34d399` | 已完成数量 |
| 逾期 | `--neon-pink` / `#fb7185` | 本周内已过去且未完成的数量 |

其他主题继续覆盖相同语义令牌，不新增硬编码的“周视图专属色”。标题使用现有 `--display-font`，任务正文使用 `--body-font`，日期和计数使用 `--utility-font`；不为一个新视图额外加载字体。

七日刻度是本页面唯一的视觉特征：今天的刻线略强，过去和未来从它向两侧自然展开。完成率圆环退居辅助位置，不再引入额外图表、装饰色块或七张卡片。这个取舍避免了通用仪表盘式的“指标卡堆叠”，同时让周的连续时间关系成为真正的页面结构。

### 7.4 任务详情列表

详情继续使用纵向日期分组，仅渲染有任务的日期，避免七个空分组拉长页面：

```text
8月11日 · 星期二 · 今天                         3
  □ 修复登录状态同步                      工作
  □ 核对移动端导航            子任务 · 首页改版
  ✓ 更新发布说明                          工作

8月13日 · 星期四                              4
  □ 提交接口联调结果                      项目 A
  ...
```

规则：

- 复用后续待办的日期标题和日期视图紧凑卡片；
- 日期标题补充“今天”或“已过期”语义；
- 任务卡片保留分组、父任务来源、完成目标、完成评价和所有现有操作；
- 任务改期后重新计算日期组和七日计数；
- 点击七日概览条中的某天，滚动时保留固定头部的可读空间；
- 已完成任务继续收纳在页面底部的可折叠区域，避免每天嵌套一个折叠面板。

第一版不做七列任务布局。当前任务缺少具体时刻和持续时长，七列只会压缩标题、描述、目标与评价；纵向分组对桌面和移动端都更稳定。

### 7.5 新建任务

本周概览继续保留新任务输入，复用后续待办的“分组 + 安排日期 + 可选完成目标”结构。

- 默认日期为今天；
- 最小日期为今天；
- 最大日期为本周周日；
- 点击未来日期概览单元后，日期输入切换到该日；
- 周日进入本视图时只能选择当天；
- 需要安排到下周或更远时，从后续待办或任务日期菜单操作；
- 保存后任务进入对应日期组，并滚动到新任务位置。

限定到本周能保持入口语义清晰。如果日期输入允许任意未来日期，本周视图中会出现“创建成功后任务立即消失”的困惑。

### 7.6 空状态

没有任何当前本周安排时：

```text
本周还没有安排
从今天开始安排一件最重要的事
```

七日概览条仍然显示，任务输入默认今天。空状态不建议展示大型插画或独立卡片，保持现有工作台的安静密度。

## 8. 方案对比与取舍

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 在今日页增加一行本周数字 | 成本最低 | 不能查看任务详情，也无法比较每天负荷 | 不采用 |
| 给后续待办增加“本周”筛选 | 复用最多 | 仍排除今天/明天；增加隐含筛选状态；入口不稳定 | 不采用 |
| 七列完整周历 | 直观，适合时间块 | 当前没有时刻和持续时长；移动端拥挤；实现成本高 | 不采用 |
| 独立本周概览：七日条 + 日期列表 | 兼顾比较、详情和移动端；复用现有渲染 | 与今日/明日范围重叠 | 推荐 |
| 周目标 + 周复盘仪式 | 能形成高层闭环 | 新概念、新数据和额外输入负担，超出本需求 | 后续单独评估 |

## 9. 技术方案

### 9.1 导航和状态

在 `main.js` 增加：

```js
const WEEK_CATEGORY_ID = 'week';
```

并将它纳入：

- `isValidCategoryId()`；
- `restoreCategoryNavigationState()`；
- `setActiveCategory()`；
- 日期导航激活态；
- `render()` 的工作区 class、标题和摘要；
- 当前账号的 `ACTIVE_CATEGORY_STORAGE_PREFIX` 记忆。

建议增加明确判断函数 `isWeekView()`，不要把所有周逻辑塞进 `isLaterView()`。

### 9.2 派生数据函数

```js
function getWeekEntries(baseDate = new Date()) {
  const { startKey, endKey } = getCurrentWeekRange(baseDate);
  return getTaskEntries()
    .filter(({ item }) => (
      item.plannedDate
      && item.plannedDate >= startKey
      && item.plannedDate <= endKey
    ))
    .sort((a, b) => (
      a.item.plannedDate.localeCompare(b.item.plannedDate)
      || compareTodoOrder(a.item, b.item)
    ));
}
```

同时增加：

- `getCurrentWeekRange()`；
- `getWeekDays()`；
- `getWeekDayStats(entries)`；
- `formatWeekRangeLabel()`；
- `renderWeekOverview()`；
- `renderWeekGroups(entries)`。

不要将 `getLaterEntries()` 改成带复杂参数的通用查询。周视图与后续视图的边界和空状态不同，保留两个简单函数更容易验证。

### 9.3 视图配置

可以扩展 `getPlannedViewConfig()`，但建议区分三类日期视图：

```text
single: 今日、明日
week:   当前周范围
range:  后天以后
```

不要只增加另一个 `isRange` 布尔值，否则新任务日期上限、空状态、工作区标题和匹配规则会出现大量交叉条件。

示意结构：

```js
{
  categoryId: WEEK_CATEGORY_ID,
  kind: 'week',
  title: '本周概览',
  startKey,
  endKey,
  emptyTitle: '本周还没有安排',
  emptyHint: '从今天开始安排一件最重要的事',
}
```

现有 today、tomorrow 和 later 可以逐步补上 `kind`，但不需要借此做无关的大规模重构。

### 9.4 渲染复用

- 进行中列表使用 `renderWeekGroups(activeEntries)`；
- 已完成列表使用同一分组函数；
- 组内卡片复用 `renderTodayEntryHtml()`；
- 日期上下文使用 `item.plannedDate`，与后续待办一致；
- 七日概览条单独渲染，不把它嵌套进任务列表卡片；
- 任务变更后第一版可以继续调用 `render()`，不必过早引入局部 diff；
- 概览条按钮的焦点和滚动目标在重绘后需要恢复。

### 9.5 数据库与 Realtime

第一版不修改：

- `supabase-schema.sql`；
- `todos` 表；
- 完成目标表；
- 完成评价表；
- 每日复盘表；
- RLS 策略和 Realtime 频道。

当前客户端已经加载用户全部任务，周聚合可完全在内存中完成。任务、目标或评价收到 Realtime 更新后，沿用现有刷新流程即可更新本周概览。

### 9.6 样式与可访问性

- 七日条使用语义化列表或带可访问名称的按钮组；
- 今天设置 `aria-current="date"`；
- 每日按钮的完整名称示例：“8月13日，星期四，4项进行中，1项已完成”；
- 颜色不能是过去、今天、逾期和完成状态的唯一提示；
- 键盘 Tab 可逐日移动，Enter/Space 跳转；
- 日期标题使用真正的标题元素，便于读屏按标题导航；
- 320px、390px、768px 和桌面宽度下检查文字不溢出；
- 遵循 `prefers-reduced-motion`，滚动跳转不强制平滑动画；
- 不在移动端构造横向任务卡片滚动区。

## 11. 验证清单

### 11.1 日期边界

- 周一打开时范围为当天到周日，同时包含本周所有当前安排；
- 周日打开时范围仍从上一个周一开始，新任务只能选择周日；
- 跨月周显示正确，例如 `8月31日 - 9月6日`；
- 跨年周显示正确，例如 `2026年12月28日 - 2027年1月3日`；
- 设备本地日期跨日后，范围、今天状态、计数和输入上下限更新；
- 夏令时环境中没有偏移一天。

### 11.2 聚合与计数

- 父任务和子任务独立计数；
- 未安排任务不出现；
- 上周逾期任务不混入本周，仍在今日往日未完成区可见；
- 本周内逾期任务保留在原日期并明确标识；
- 下周任务不出现；
- 进行中、已完成、每日统计和完成率口径一致；
- 清除已完成的安排后，所有当前快照指标同步变化。

### 11.3 任务操作

- 改期到本周另一日后移动到正确日期组；
- 改期到下周后从本周概览消失，并有明确成功提示；
- 取消安排后消失；
- 完成或重新打开后在进行中与已完成区之间移动；
- 新任务只能选择今天至周日；
- 新任务保存后出现在正确日期并恢复焦点；
- 父任务和子任务操作不发生日期级联。

### 11.4 目标与评价

- 卡片显示安排日的精确完成目标；
- 没有精确目标时只显示符合现有规则的上次目标；
- 今天和过去日期可显示或编辑对应评价；
- 未来日期不能提前评价；
- 改期后不把旧评价误当成新日期评价；
- 每日复盘正文不会自动混入本周任务列表。

### 11.5 响应式与可访问性

- 七日条在 320px 宽度下不溢出；
- 长任务名、长分组名和双位数任务量不挤压相邻日期；
- 移动端侧栏入口可达，关闭抽屉后焦点合理；
- 键盘可操作七日条、任务卡片和日期调整；
- 读屏能获得完整日期与计数，不依赖颜色；
- 减少动画偏好下不强制平滑滚动。

## 12. 验收标准

满足以下条件即可认为第一版完成：

1. 用户能从侧栏进入“本周概览”，刷新和重新登录后视图状态可恢复；
2. 页面固定展示当前周一至周日的范围，并正确处理跨月与跨年；
3. 七日概览能区分每天的进行中、已完成、今天和本周内逾期状态；
4. 任务详情按日期分组，父任务和子任务与今日/后续视图的语义一致；
5. 用户能在视图中完成、改期、取消安排和创建本周任务；
6. 顶部指标与侧栏计数明确遵守当前快照口径；
7. 不新增数据库结构，不把 `planned_date` 当成历史周报来源；
8. 桌面端、移动端、键盘和读屏使用均通过验证。

## 13. 后续演进条件

上线后先观察以下问题，而不是直接扩展为完整周报：

- 用户是否高频从概览改期，还是只查看；
- 七日负荷是否足够，是否真的需要跨周翻页；
- 用户是否需要按分组筛选本周任务；
- 用户是否希望看到已经清除安排的历史完成项；
- 用户是否会主动填写任务完成评价和今日复盘；
- 用户是否需要少量独立“周目标”，而不是任务总数；
- 用户是否需要导出或分享周总结。

只有当“回看历史周实际工作”成为明确需求时，才进入第二个独立方案。届时至少需要先确定稳定事实来源：

```text
完成评价记录
    + 完成时间
    + 每日复盘
    + 必要时新增计划变更事件或周快照
```

不能仅扩展本周概览到上周并称为周报，因为可变 `planned_date` 无法还原历史安排。
