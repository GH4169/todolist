# 按日期记录的完成目标设计方案

> 文档状态：产品与交互方案已收敛，可作为后续实现依据  
> 最后更新：2026-07-31  
> 适用范围：父任务、子任务、今日待办、明日待办、普通分组视图

## 1. 一句话定义

“完成目标”是任务自身拥有的一组、按日期保存的阶段目标。

一个父任务或子任务可以跨越多天，每一天都能写下当天需要推进到什么程度；任务卡片默认只显示与当前场景最相关的一条最近目标，旧目标持续保存，但历史记录默认折叠。

示例：

```text
任务：完成毕业论文

7月31日完成目标：完成第二章结构并写完前 1500 字
8月1日完成目标：补齐案例分析，形成第二章初稿
8月2日完成目标：根据导师反馈完成第二轮修改
```

这些目标都属于“完成毕业论文”这个任务。它们不是独立待办，也不是额外的每日任务副本。

## 2. 已确认的需求理解

### 2.1 完成目标属于任务本身

- 父任务可以拥有完成目标。
- 每个子任务也可以拥有自己的完成目标。
- 目标记录随任务保存、同步和删除。
- 目标不是工作区级别的数据，也不是与任务松散关联的日记。

### 2.2 每条目标必须绑定日期

完成目标不能只保存一段会不断被覆盖的文本。每条目标至少由以下内容组成：

- 所属任务；
- 目标日期；
- 目标文字；
- 创建时间；
- 最后修改时间。

### 2.3 一个任务可以积累多天的目标

任务跨日推进时，新一天应新增一条目标，而不是修改旧目标的日期或覆盖旧文字。

```text
7月31日：完成首页桌面端
8月1日：完成首页移动端
8月2日：完成交互检查与修复
```

### 2.4 卡片只显示一条最近目标

- 父任务卡片最多显示一条。
- 子任务行或子任务卡片最多显示一条。
- 不在卡片中平铺历史，不把任务列表变成日志页面。
- 需要查看旧目标时，通过“目标历史”入口打开。

### 2.5 历史始终保存，但默认不展示

“默认关闭历史记录”在本方案中定义为：

- 历史记录功能始终生效，旧目标不会因界面折叠而停止保存；
- 历史区域每次打开目标面板时默认处于折叠状态；
- 用户主动点击“历史目标”后才展示时间线；
- 第一版不需要增加全局设置，也不记忆历史区域的展开状态。

这避免了一个危险歧义：如果把“关闭历史”实现为“不记录历史”，用户会在无意间失去跨日推进轨迹。

## 3. 它与现有字段的区别

| 字段 | 回答的问题 | 示例 |
| --- | --- | --- |
| 任务标题 | 最终要做什么？ | 完成毕业论文 |
| 任务描述 | 有什么背景、资料或注意事项？ | 参考导师批注，数据见附件 |
| 安排日期 | 准备在哪一天继续处理？ | 8月1日 |
| 完成目标 | 在绑定的那一天需要推进到哪里？ | 完成第二章初稿并自查引用 |
| 子任务进度 | 已完成了多少个步骤？ | 子任务 2/5 |
| 完成状态 | 整个任务是否已经结束？ | 未完成 |

完成目标不能替代任务描述，也不能替代子任务进度。

- 完成目标是文字表达的阶段边界。
- `子任务 2/5` 是系统计算的客观进度。
- 顶部完成率仍表示当前视图中任务的勾选情况。

## 4. 相似产品模式调研

目前没有发现一个主流任务产品与本需求完全一致。最接近的是以下三类机制的组合。

### 4.1 Linear / Asana：最新状态突出，旧更新进入历史

项目或目标的周期状态更新通常采用两层结构：

- 页面首先呈现最近一次更新，帮助用户快速判断当前状态；
- 过去的更新按时间排列，需要时再进入历史或活动流查看。

可借鉴之处：

- “当前要看的内容”和“可追溯历史”应该分离；
- 历史不应抢占日常列表的视觉空间；
- 每次更新都应带时间语义，而不是只覆盖一个永远变化的字段。

不直接照搬之处：

- 这些产品的状态更新通常属于项目或目标层级，并不天然覆盖普通任务和子任务；
- 它们常包含状态颜色、风险和评论，本项目只需要一段明确的完成边界，应该更轻量。

### 4.2 Jira / ClickUp：当前字段与变更记录分离

任务系统通常在任务主体上显示当前字段值，而把字段的历史变更放在 Activity、History 或 Audit 区域。

可借鉴之处：

- 卡片只显示当前最相关的值；
- 历史通过独立入口查看；
- 父任务和子任务均是独立任务实体，各自保有字段和历史。

不直接照搬之处：

- 通用活动流会混入标题修改、负责人修改、评论等大量噪声；
- 本项目应该只展示“完成目标历史”，不建立一个复杂的全量审计日志界面。

### 4.3 每日计划产品：未完成任务继续滚动，但阶段承诺需要重新确认

每日计划类产品通常允许未完成任务被顺延到下一天。最值得借鉴的不是“自动滚动”本身，而是：

- 任务身份保持不变；
- 日期计划可以改变；
- 昨天的计划事实不应因为顺延而消失；
- 下一天需要重新确认今天准备完成到哪里。

这与本需求高度一致：移动任务日期时保留旧目标，并为新日期创建新的完成目标。

### 4.4 调研结论

本项目最适合采用以下组合：

```text
任务实体
  └─ 多条按日期保存的完成目标
       ├─ 卡片只投影一条当前目标
       └─ 编辑面板中按需展开历史时间线
```

这比“任务上只有一个完成程度字段”更接近项目状态更新；又比完整 Activity 日志更聚焦、更适合个人效率工具。

### 4.5 参考资料与核对说明

建议后续实现前再次核对以下官方帮助主题：

- Linear：Project updates
- Asana：Project status updates / Goal status updates
- Jira：Issue history / Activity
- ClickUp：Task activity / Custom field history

## 5. 推荐的信息架构

### 5.1 产品命名

用户概念可以继续称为“完成程度”，但界面字段推荐使用“完成目标”。

原因：

- “完成程度”容易被理解为 `60%`、`2/5` 等已经发生的进度；
- “完成目标”更准确地表示某个日期希望推进到的状态；
- 日期视图中可以自然写成“今日完成目标”和“明日完成目标”。

推荐界面文案：

| 场景 | 文案 |
| --- | --- |
| 今日待办 | 今日完成目标 |
| 明日待办 | 明日完成目标 |
| 普通分组 | 完成目标 · 8月1日 |
| 沿用过期目标 | 上次目标 · 7月30日 |
| 新增入口 | 设定完成目标 |
| 历史入口 | 历史目标 3 |
| 输入提示 | 例如：完成第二章初稿，至少写到 5000 字 |

### 5.2 所有权关系

完成目标直接关联具体的 todo 记录。因此父任务和子任务使用完全相同的数据结构。

```text
父任务 A
├─ 父任务 A 的完成目标历史
├─ 子任务 A1
│  └─ 子任务 A1 的完成目标历史
└─ 子任务 A2
   └─ 子任务 A2 的完成目标历史
```

父任务目标与子任务目标之间：

- 不继承；
- 不自动复制；
- 不自动汇总；
- 不因子任务全部完成而自动修改文字；
- 可以只填写其中一个层级，也可以两个层级都填写。

## 6. “最近目标”的确定规则

这是实现中必须统一的核心算法。

### 6.1 今日 / 明日视图

假设当前视图日期为 `contextDate`：

1. 如果任务存在 `target_date = contextDate` 的目标，显示该目标。
2. 如果没有当天目标，查找日期早于 `contextDate` 的目标，显示其中日期最新的一条，并标记为“上次目标”。
3. 不显示晚于 `contextDate` 的未来目标，避免未来计划覆盖今天应该看到的要求。
4. 如果既没有当天目标也没有过去目标，显示轻量入口“设定今日完成目标”或“设定明日完成目标”。

伪代码：

```js
function getGoalForPlannedView(goals, contextDate) {
  const exact = goals.find(goal => goal.targetDate === contextDate);
  if (exact) return { goal: exact, state: 'exact' };

  const previous = goals
    .filter(goal => goal.targetDate < contextDate)
    .sort(byTargetDateDesc)[0];

  return previous
    ? { goal: previous, state: 'carried' }
    : { goal: null, state: 'missing' };
}
```

### 6.2 普通分组视图

普通分组没有明确的上下文日期，因此显示目标日期最新的一条：

```js
const latestGoal = goals.sort(byTargetDateDesc)[0] || null;
```

必须同时显示目标日期，不能只显示文字，否则未来目标和过去目标会失去语义。

### 6.3 同一天只能有一条目标

一个任务在同一个目标日期最多保存一条完成目标。

- 修改同一天的文字：更新现有记录。
- 为新的一天设定目标：创建新记录。
- 不把同一天的每一次文字修改都当作一条历史。

本功能的“历史”是按日期形成的阶段目标历史，不是逐键编辑版本历史。

## 7. 日期变化与顺延规则

### 7.1 从今天移到明天

操作结果：

- 更新任务的 `planned_date` 为明天；
- 今天的完成目标保留在历史中；
- 如果明天已经有目标，直接使用；
- 如果明天没有目标，打开一个轻量编辑步骤，请用户填写明日完成目标；
- 可以提供“沿用上次目标”快捷操作，但不得自动复制。

原因：自动复制会让“今天没完成的承诺”伪装成“明天主动制定的新目标”，降低历史可信度。

### 7.2 往日未完成移到今天

- 旧日期目标继续保留；
- 任务进入今天后，卡片暂时显示最近的过去目标，标签为“上次目标 · 日期”；
- 同时提供明显但克制的“更新今日目标”入口；
- 用户保存后新增今天的目标，卡片立即改为“今日完成目标”。

### 7.3 取消安排日期

- 只清空 `planned_date`；
- 所有完成目标均保留；
- 普通分组视图仍可显示日期最新的一条目标；
- 不因取消安排而删除历史。

### 7.4 任务完成与重新打开

- 任务完成后，完成目标历史保留；
- 已完成卡片仍显示最近目标，但整体弱化；
- 重新打开任务时不自动创建新目标；
- 用户重新安排日期后，再按正常规则设定该日期目标。

## 8. 界面方案

### 8.1 设计原则

- 完成目标是日期视图中仅次于标题的重要信息。
- 历史是辅助信息，默认隐藏。
- 新增区域只使用现有今日橙和明日蓝，不引入第三套强强调色。
- 卡片不能同时展示多个历史目标。
- 文字最多展示两行，超出后截断；点击目标区域进入完整编辑面板。

### 8.2 今日待办中的父任务

```text
┌─────────────────────────────────────────────┐
│ □  完成移动端重构                     ···   │
│                                             │
│    今日完成目标                             │
│    首页和任务列表达到可测试状态，完成       │
│    390px 与 430px 两种尺寸检查              │
│                                             │
│    产品开发  ·  子任务 2/5                 │
└─────────────────────────────────────────────┘
```

布局层级：

1. 标题；
2. 今日完成目标；
3. 分组、时间、子任务进度等元信息；
4. 操作按钮。

目标区域建议使用左侧短线或极浅色底，而不是再增加粗进度条。

### 8.3 明日待办中的父任务

结构与今日一致，仅替换语境：

```text
明日完成目标
完成详情页适配，并整理第一轮交互问题
```

- 今日使用当前的橙色语义；
- 明日使用当前的蓝色语义。

### 8.4 日期视图中的独立子任务

```text
┌─────────────────────────────────────────────┐
│ 子任务                                      │
│ □  适配任务列表                             │
│                                             │
│    今日完成目标                             │
│    完成列表布局，交互问题留待明天处理       │
│                                             │
│    来自：完成移动端重构 · 产品开发          │
└─────────────────────────────────────────────┘
```

子任务目标只描述这个子任务，不展示或继承父任务目标。

### 8.5 普通分组中的父子树

父任务展开状态：

```text
□ 完成移动端重构
  完成目标 · 8月1日
  首页和任务列表达到可测试状态

  □ 适配首页
    完成目标 · 8月1日
    完成两种移动端宽度检查

  □ 适配任务列表
    完成目标 · 7月31日
    完成基础布局
```

规则：

- 父任务只显示父任务自己的最近目标；
- 每个子任务只显示自己的最近目标；
- 父任务折叠后不摘要展示所有子任务目标；
- 没有目标的任务在普通分组中不占用额外空行；
- 没有目标的任务只在今日 / 明日视图中显示设定入口。

### 8.6 父任务和子任务同时安排到同一天

第一版继续采用当前日期视图的平铺模式：

- 父任务是一张卡片，显示父任务目标；
- 被独立安排的子任务也是一张卡片，显示子任务目标和父任务来源；
- 不在第一版引入复杂的自动分组或嵌套日期卡片。

理由：

- 父任务目标可能是整体质量边界，子任务目标是具体推进边界，两者并不重复；
- 平铺更适合快速扫描今天必须处理的独立承诺；
- 自动聚合会改变当前完成率、排序和拖拽语义，应作为独立需求验证。

如果后续实际使用中出现明显重复感，可再设计“按父任务聚合今日条目”，但不应阻塞本功能第一版。

## 9. 目标编辑与历史面板

### 9.1 打开方式

- 点击卡片上的当前目标文字；
- 点击没有目标时的“设定完成目标”；
- 在任务操作菜单中选择“完成目标”；
- 安排到今日或明日后，如果目标缺失，自动打开轻量编辑面板。

### 9.2 桌面端

复用项目现有 `<dialog>` 视觉体系，建议宽度约 `520px`：

```text
┌─────────────────────────────────────────────┐
│ 完成目标                              ×     │
│ 完成移动端重构                              │
│                                             │
│ 目标日期                                    │
│ [ 2026-08-01 ]                              │
│                                             │
│ 需要推进到                                  │
│ [ 首页和任务列表达到可测试状态……       ]   │
│                                             │
│ ▸ 历史目标 3                                │
│                                             │
│                         取消   保存目标      │
└─────────────────────────────────────────────┘
```

### 9.3 移动端

- 可以继续使用居中对话框，但宽度接近视口并限制高度；
- 更推荐后续实现为底部 sheet；
- 历史展开后内部滚动，不让整个页面背景滚动；
- 日期与正文输入保持在面板顶部，保存按钮固定在底部。

第一版为了复用已有组件，可以先用响应式 dialog，不必为了本功能引入一整套 sheet 基础设施。

### 9.4 历史展开状态

```text
⌄ 历史目标 3

8月1日
首页和任务列表达到可测试状态

7月31日
完成首页桌面端并整理剩余问题

7月30日
确定断点与移动端信息层级
```

- 按目标日期倒序排列；
- 当前正在编辑的记录也可以出现在时间线顶部，并标记“当前”；
- 默认只展开最近 5 条，更多记录通过“查看更多”加载；
- 历史条目显示目标日期，必要时弱化显示最后修改时间；
- 不展示创建人，因为当前产品是个人任务工具。

### 9.5 编辑与删除历史

建议第一版支持：

- 编辑任意日期的目标；
- 删除任意一条目标，需要二次确认；
- 新增其他日期的目标；
- 修改日期时，如果目标日期发生冲突，提示“该日期已有目标”，让用户选择取消或覆盖，不能静默合并。

删除目标不删除任务，也不改变任务完成状态。

## 10. 新建与安排流程

### 10.1 在今日 / 明日视图新建父任务

日期视图的快速输入建议扩展为两层：

```text
[ 任务标题：接下来要完成什么？       ] [目标] [+]
[ 今日完成目标：今天至少推进到哪里？（可选） ]
```

- 第一行必填；
- 第二行可选，默认收起；点击标题输入行右侧的目标图标后展开，并自动聚焦目标输入；
- 两条记录应在同一提交操作中完成；
- 如果目标保存失败而任务已创建，应明确提示并保留任务，不能整项静默消失。

第一版不建议强制填写目标。快速捕获仍然重要；没有目标的日期卡片应提供明显的补充入口。

### 10.2 在普通分组中新建父任务

- 保持当前快速添加不变；
- 创建后可通过任务操作进入“完成目标”；
- 默认目标日期：优先使用任务的 `planned_date`，否则使用今天。

### 10.3 给现有父任务或子任务安排日期

用户在日期菜单中选择今天或明天时：

1. 更新任务安排日期；
2. 检查该日期是否已有完成目标；
3. 已有目标：正常完成安排；
4. 没有目标：打开目标输入；
5. 用户可以保存，也可以选择“稍后填写”。

### 10.4 新增子任务

普通分组中的子任务新增行维持简洁，只输入标题。子任务创建后可独立安排日期并设定目标。

若未来要支持“在今日待办中直接添加某父任务的子任务”，再为该流程增加目标输入，不应在第一版扩大范围。

## 11. 日期的双重语义

本功能引入后，任务上会同时出现两个日期概念，必须明确区分：

- `todos.planned_date`：任务当前被安排在哪一天处理；一个任务当前只有一个安排日期。
- `todo_completion_goals.target_date`：某条阶段目标对应哪一天；一个任务可以保留很多目标日期。

关系示例：

```text
任务当前 planned_date = 8月2日

目标历史：
7月31日  完成页面结构
8月1日   完成桌面端
8月2日   完成移动端
```

这仍然符合“完成目标属于任务本身”：目标记录通过 `todo_id` 归属于任务；日期只是这条任务属性记录的生效维度，而不是把目标变成独立待办。

### 11.1 第一版的单日安排限制

当前 `planned_date` 只能让同一个任务直接出现在一个日期视图中。目标表虽然可以预先保存今天和明天两条目标，但任务本身不会因此同时出现在今日与明日两个列表。

第一版保留这个限制：

- 目标历史支持多日期；
- 任务的当前安排仍为单日期；
- 用户把任务从今天改到明天时，今天目标进入历史，明天目标成为当前显示目标。

如果未来明确需要“同一个任务同时出现在今日和明日待办”，应另行把任务安排也改成一对多表；不能仅靠目标记录决定日期列表成员，否则安排语义与目标语义会再次混在一起。

## 12. 数据库设计

### 12.1 不推荐的设计

不要只在 `todos` 表增加：

```sql
completion_goal text,
completion_goal_date date
```

这种设计只能保存一条目标，跨日修改时历史必然丢失；后续再补历史会产生复杂迁移。

### 12.2 推荐新表

```sql
create table if not exists public.todo_completion_goals (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid()
    references auth.users(id) on delete cascade,
  todo_id uuid not null,
  target_date date not null,
  content text not null
    check (length(trim(content)) between 1 and 500),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint todo_completion_goals_todo_owner_fkey
    foreign key (todo_id, user_id)
    references public.todos(id, user_id)
    on delete cascade,

  constraint todo_completion_goals_one_per_day
    unique (todo_id, target_date)
);
```

索引：

```sql
create index if not exists todo_completion_goals_user_todo_date_idx
  on public.todo_completion_goals(user_id, todo_id, target_date desc);
```

需要沿用现有项目的：

- `updated_at` trigger；
- authenticated 权限；
- 按 `user_id = auth.uid()` 的 RLS；
- 私有 Realtime Broadcast；
- 删除任务时数据库级联删除目标。

### 12.3 为什么不保存 `is_current`

不建议增加 `is_current` 字段。

“当前显示哪一条”由目标日期和界面上下文计算得出。增加 `is_current` 会带来双重事实来源：日期最新的记录与被标记为 current 的记录可能不一致。

### 12.4 客户端模型

父任务和子任务映射后均包含：

```js
{
  id,
  text,
  plannedDate,
  completionGoals: [
    {
      id,
      todoId,
      targetDate: '2026-08-01',
      content: '首页和任务列表达到可测试状态',
      createdAt,
      updatedAt,
    },
  ],
}
```

目标数组在客户端统一按 `targetDate DESC` 排序。

## 13. 数据访问与实时同步

建议在 `js/storage.js` 增加：

- `loadCompletionGoals()`；
- `createCompletionGoalRecord()`；
- `updateCompletionGoalRecord()`；
- `deleteCompletionGoalRecord()`；
- `upsertCompletionGoalForDate()`；
- 目标记录的 map 函数。

加载流程可采用：

1. 并行加载 todos、categories、completion goals；
2. 先组装父子任务；
3. 再按 `todo_id` 把目标挂到父任务或子任务；
4. 渲染前保证每个任务都有 `completionGoals: []`。

Realtime 建议使用独立 topic：

```text
todo-completion-goals:{userId}
```

收到 insert / update / delete 后：

- 更新对应任务的目标数组；
- 重新排序；
- 只重绘受影响的父任务或当前日期列表；
- 重新计算目标缺失状态，但不影响完成率。

完成目标不参与：

- 顶部完成率；
- 进行中 / 已完成计数；
- 子任务完成数量；
- 任务排序。

## 14. 关键业务规则

1. 父任务和子任务都能有目标历史。
2. 每个任务每个日期最多一条目标。
3. 同一天编辑是更新，不产生第二条历史。
4. 新日期保存是新增，不覆盖旧日期。
5. 更改 `planned_date` 不删除、迁移或重写目标日期。
6. 卡片最多显示一条目标。
7. 日期视图优先显示当天目标。
8. 日期视图没有当天目标时，只能回看最近过去目标，不能显示未来目标。
9. 普通分组显示日期最新的一条目标，并明确标日期。
10. 目标文字为空时不保存记录；清空已有文字应视为删除并确认。
11. 目标不自动继承，不自动从父任务复制到子任务。
12. 子任务全部完成仍按现有逻辑影响父任务完成状态，但不修改父任务目标。
13. 删除任务通过外键级联删除其目标历史。
14. 历史区域默认折叠，折叠状态不需要持久化。

## 15. 边界情况

### 15.1 只有未来目标，但任务被安排到今天

- 今天卡片不展示未来目标；
- 显示“设定今日完成目标”；
- 编辑面板历史中仍能看到未来目标，并标记日期。

### 15.2 只有昨天目标，任务被顺延到今天

- 卡片展示昨天目标；
- 标签写“上次目标 · 7月30日”；
- 提供“更新今日目标”；
- 不能把昨天标签伪装成“今日完成目标”。

### 15.3 同一天先后多次调整目标

- 保留一条记录；
- 更新 `content` 和 `updated_at`；
- 第一版不提供同日文字修订历史。

### 15.4 修改目标日期产生冲突

- 不静默覆盖；
- 提示该日期已有目标；
- 用户可以取消，或明确选择用当前内容替换该日目标；
- 被替换记录的处理方式需要实现时固定为“更新已有记录并删除当前记录”，避免违反唯一约束。

### 15.5 任务跨时区同步

- `target_date` 使用数据库 `date`，不存时区；
- 日期含义与现有 `planned_date` 一致，按用户本地日历日处理；
- `created_at`、`updated_at` 继续使用 `timestamptz`。

### 15.6 很长的目标文字

- 数据库上限建议 500 字符；
- 卡片最多两行并截断；
- 编辑面板展示全文；
- 移动端不横向滚动。

## 16. 可访问性

- 目标块如果可点击，必须使用 `<button>` 或明确的可聚焦控件，不能只给 `<div>` 绑定点击。
- 目标按钮的无障碍名称应包含任务名和日期，例如“编辑完成移动端重构的今日完成目标”。
- 历史折叠按钮使用 `aria-expanded` 和 `aria-controls`。
- 日期输入必须有可见标签。
- 今日橙 / 明日蓝不能作为唯一信息来源，必须同时有文字标签。
- 对话框打开后聚焦目标输入，关闭后把焦点还给触发按钮。
- 删除历史需要确认，并提供明确的目标日期。

## 18. 验收标准

### 数据

- [ ] 父任务可以保存多个不同日期的目标。
- [ ] 子任务可以保存多个不同日期的目标。
- [ ] 同一任务同一天不能出现两条目标。
- [ ] 修改新日期目标不会覆盖旧日期目标。
- [ ] 删除任务会级联删除目标记录。
- [ ] 目标可在多设备实时同步。

### 显示

- [ ] 每张父任务卡最多展示一条目标。
- [ ] 每个子任务最多展示一条目标。
- [ ] 今日视图优先显示今日目标。
- [ ] 明日视图优先显示明日目标。
- [ ] 没有当天目标时，过去目标被明确标为“上次目标”。
- [ ] 未来目标不会错误地显示为今日目标。
- [ ] 普通分组展示日期最新目标并显示日期。
- [ ] 历史默认折叠。

### 交互

- [ ] 安排任务到今天或明天时可以立即填写对应目标。
- [ ] 用户可以选择稍后填写，不阻塞快速添加。
- [ ] 顺延任务不会删除旧目标。
- [ ] 可以展开历史并按日期倒序查看。
- [ ] 可以编辑、删除和新增目标。
- [ ] 日期冲突不会被静默覆盖。

### 非回归

- [ ] 完成目标不改变现有完成率算法。
- [ ] 完成目标不改变父子任务完成联动。
- [ ] 完成目标不改变当前排序和拖拽。
- [ ] 现有任务描述继续独立工作。
- [ ] 没有目标的旧任务无需数据迁移即可正常显示。

## 19. 后续实现时不要重新讨论的决定

除非用户明确改变需求，后续 AI 应直接采用以下决定：

1. 使用独立目标表，不在 `todos` 上保存单一目标文本。
2. 目标历史属于任务，父任务和子任务结构相同。
3. 一个任务一天一条目标。
4. 历史是按日期的目标历史，不是同日编辑审计日志。
5. 历史始终记录，界面默认折叠。
6. 卡片只展示一条目标。
7. 今日 / 明日优先显示与视图日期相同的目标。
8. 日期视图不能拿未来目标冒充当天目标。
9. 顺延任务保留旧目标，并鼓励为新日期创建目标。
10. 第一版保持日期视图父任务和独立子任务平铺，不做自动聚合。
11. 完成目标不参与任何现有完成率和任务完成逻辑。

## 21. 视觉规格补充

### 21.1 紧凑目标块

目标块不是新的大卡片，而是任务卡片内部的“阶段刻度”。建议：

```text
左侧 2px 日期色短线
标签：utility 字体，0.56rem–0.62rem，半粗体
正文：0.76rem–0.84rem，1.55 行高，最多两行
块间距：标题后 8px，元信息前 8px
背景：极浅混色，不能比任务卡主体更亮
```

普通分组子任务中的目标再缩小一级，避免父子树过于松散。

### 21.2 一处有辨识度的设计

本功能唯一的特色元素是“日期刻度线”：

```text
│ 今日完成目标
│ 首页和任务列表达到可测试状态
```

它表达这是任务推进时间线上的一个阶段刻度，而不是装饰。其他地方保持安静，不增加徽章堆叠、渐变进度条或新的图标体系。

### 21.3 目标状态样式

| 状态 | 标签 | 视觉处理 |
| --- | --- | --- |
| 当天目标 | 今日完成目标 / 明日完成目标 | 使用对应日期强调色 |
| 沿用过去目标 | 上次目标 · 7月30日 | 使用弱化文字和虚线刻度 |
| 普通分组最新目标 | 完成目标 · 8月1日 | 通用蓝或当前主题主色 |
| 缺失目标 | 设定今日完成目标 | 轻量虚线按钮，不占两行正文高度 |
| 已完成任务 | 原标签 | 随卡片整体降低透明度，不额外划线 |
