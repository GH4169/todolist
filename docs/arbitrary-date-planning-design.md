# 父任务与子任务的任意日期安排设计方案

> 文档状态：合理性评估与方案调研已完成，可作为后续实现依据
>
> 最后更新：2026-07-31
>
> 适用范围：父任务、子任务、今日待办、明日待办、后续待办、普通分组视图

## 1. 结论

该需求合理，建议实现，但应把“选择其他日期”和“之后从哪里找到这些任务”作为一个完整功能交付。

推荐方案：

1. 保留现有“今天”“明天”两个高频快捷项；
2. 在“安排日期”菜单中增加“选择日期…”；
3. 只允许主动选择今天及未来日期；
4. 在侧栏增加“后续待办”，集中展示后天及更远日期的任务，并按日期分组；
5. 父任务和子任务继续独立安排，不自动级联；
6. 复用现有 `planned_date date`，不修改数据库结构。

不建议只增加一个日期输入框而不增加“后续待办”。那会让任务可以被安排到后天，却没有稳定的跨分组入口用于找回、检查和调整，产品链路不完整。

## 2. 合理性评估

### 2.1 用户价值成立

现有“今天/明天”适合短期执行，但不能表达以下常见计划：

```text
周五提交周报
下周一联系供应商
8月15日续费证书
月底前复查合同
```

用户目前只能把这类任务留在普通分组，等到前一天再手动安排。这样会产生两个问题：

- 计划信息只能写进标题或描述，无法被系统识别和汇总；
- 用户必须自己记住何时回来重新安排，日期功能没有承担计划职责。

允许选择未来日期后，“安排日期”才真正回答：

> 我准备在哪一天继续处理这项任务？

这与现有完成目标和每日完成评价形成一致的日期链路：

```text
安排日期：8月3日
    ↓
8月3日完成目标：完成接口联调并整理问题清单
    ↓
8月3日完成评价：部分达成，剩余一个权限问题
```

### 2.2 与现有产品模型一致

当前模型已经具备通用日期能力：

- 父任务和子任务都保存为 `todos` 记录；
- 两者都使用可空的 `planned_date date`；
- 客户端已经把数据库值映射为 `plannedDate`；
- 当前日期视图通过 `plannedDate === dateKey` 精确筛选；
- 往日未完成通过规范化的 `YYYY-MM-DD` 字符串比较识别；
- `planned_date` 已有按用户和日期建立的部分索引。

因此，这不是一次数据模型扩张，而是解除界面只提供今天和明天的限制。

### 2.3 复杂度可控

功能不需要引入：

- 新表或新字段；
- 时刻和时区换算；
- 提醒通知；
- 重复任务规则；
- 第三方日历同步；
- 完整的月/周日历布局。

主要工作集中在日期选择、后续任务聚合、日期上下文渲染和测试，范围清晰。

### 2.4 风险与成立条件

| 风险 | 影响 | 约束方式 |
| --- | --- | --- |
| 未来任务安排后难以找回 | 用户不敢使用任意日期 | 同期提供“后续待办” |
| 日期菜单变得过重 | 高频的今天/明天操作变慢 | 保留快捷项，月历放入独立对话框 |
| 日期含义被误解为截止日期 | 用户期待逾期提醒或强约束 | 继续使用“安排日期”，不改称“截止日期” |
| 父子任务日期互相覆盖 | 破坏现有独立任务语义 | 父子任务独立保存，不自动继承或级联 |
| 本地日期转换偏移一天 | 跨时区设备出现错误日期 | 始终保存本地日历日字符串，不转 UTC 时间戳 |
| 计划范围无限增长 | “后续待办”列表过长 | 按日期分组，只渲染有任务的日期，完成区默认折叠 |

综合判断：收益明确、模型已支持、风险可通过交互和视图设计控制，建议进入实现。

## 3. 现状核对

### 3.1 当前入口

父任务和子任务都已有日历图标按钮。点击后打开轻量菜单：

```text
今天       7月31日
明天       8月1日
──────────────
取消安排   保留在原分组
```

按钮已经能识别三种状态：

- 今天：橙色选中态；
- 明天：蓝色选中态；
- 其他非空日期：通用 `is-scheduled` 状态。

这说明渲染层已经考虑过“其他日期”，只是菜单没有提供写入入口。

### 3.2 当前日期视图

侧栏只有：

- 今日待办：`planned_date = 今天`；
- 明日待办：`planned_date = 明天`。

今日视图还会展示 `planned_date < 今天` 的未完成任务，并允许移动到今天。后天及更远日期目前没有聚合视图。

### 3.3 当前保存流程

`setTodoPlannedDate(id, plannedDate)` 已经接受任意日期值，并通过统一的存储映射更新 `planned_date`。保存成功后，如果新日期没有完成目标，会继续打开该日期的完成目标面板。

需要修正的现有假设是：成功提示只区分今天、明天和取消安排。传入其他非空日期时目前会错误显示“已取消日期安排”。

## 4. 同类产品调研

### 4.1 Microsoft To Do

Microsoft To Do 的官方帮助说明中，截止日期提供“今天、明天、下周、选择日期”等入口；设置日期后，任务会自动进入 Planned 智能列表，可查看今天、明天及更远日期的任务。

可借鉴之处：

- 高频相对日期与自选日期同时存在；
- 设置日期后有统一的计划列表承接；
- “自选日期”不是一个孤立字段，而是计划视图的信息来源。

不直接照搬之处：

- 本项目的 `planned_date` 表示准备处理日期，不应改成强约束的“截止日期”；
- 第一版不增加提醒、重复和具体时刻。

### 4.2 Todoist

Todoist 的官方帮助显示，日期调度支持今天、明天、星期、相对天数和具体日期；Upcoming 视图可以跨项目查看未来 7 天及更远日期，并按日期继续浏览和重新安排。

可借鉴之处：

- 今天仍是执行视图，未来计划另有统一入口；
- 未来任务按日期组织，而不是为每个日期创建侧栏导航；
- 调整安排日期应当是任务上的轻量操作。

不直接照搬之处：

- 本项目没有自然语言日期解析基础，不在第一版引入；
- 本项目是轻量列表工具，不引入完整日历布局、拖拽排期或两年范围的日期导航。

### 4.3 调研结论

两个产品的共同模式是：

```text
快捷日期 + 自选日期 + 统一的未来计划入口
```

这印证了本方案的关键判断：如果只做“自选日期”，任务会被写入未来，但缺少后续管理面；如果同时增加完整月历，又超出当前应用的复杂度。最适合本项目的是紧凑菜单、原生日期输入和按日期分组的后续列表。

## 5. 产品定义与边界

### 5.1 继续使用“安排日期”

`planned_date` 的语义保持不变：

> 用户准备在哪一个本地日历日继续处理任务。

它不是：

- 必须完成的截止日期；
- 自动通知时间；
- 任务开始时间与结束时间；
- 任务每天重复出现的规则；
- 完成目标或完成评价的日期替代品。

### 5.2 第一版支持范围

- 今天；
- 明天；
- 后天及任意更远的未来日期；
- 清除已有安排；
- 已自然过期的历史安排重新安排到今天或未来。

### 5.3 第一版不支持范围

- 主动把任务安排到过去；
- 具体时刻；
- 提醒通知；
- 重复计划；
- 日期区间和持续天数；
- 工作日/节假日规则；
- 自然语言输入；
- 月历和周历视图；
- 父任务对子任务的自动日期继承；
- 子任务自动汇总出父任务日期。

不允许主动选择过去日期，是因为 `planned_date` 保存的是当前计划而非历史记录。历史执行事实已经由按日期完成目标和完成评价承载；新建一个立即过期的计划没有稳定价值，还会直接进入“往日未完成”。

## 6. 信息架构

### 6.1 侧栏日期导航

推荐增加第三个日期导航项：

```text
今日待办      3
明日待办      2
后续待办      7
```

三者形成互斥的未来日期分区：

| 入口 | 进行中任务范围 |
| --- | --- |
| 今日待办 | `planned_date = 今天`，另显示往日未完成提示区 |
| 明日待办 | `planned_date = 明天` |
| 后续待办 | `planned_date > 明天` |

“后续待办”计数只统计未完成的父任务和子任务，沿用今日/明日计数口径。

不使用“日历”作为名称，因为第一版不是月历；不使用“计划”作为名称，是为了避免与“完成目标”及普通分组中的宽泛计划概念混淆。

### 6.2 后续待办列表

进行中的任务按 `planned_date` 升序分组，只渲染有任务的日期：

```text
后续待办
未来 3 个日期 · 7 项进行中

8月2日 · 星期日                         2
  □ 完成移动端适配
  □ 核对支付回调                    子任务

8月5日 · 星期三                         1
  □ 提交月度报表

8月15日 · 星期六                        4
  ...
```

组内顺序沿用现有任务顺序规则，不因为增加任意日期而引入第二套手动排序。

父任务和子任务继续按日期视图的平铺模式呈现：

- 父任务显示所属分组；
- 子任务显示“子任务”标记、父任务标题和所属分组；
- 父任务与子任务安排在同一天时，作为两条独立记录出现；
- 子任务出现不要求父任务也安排在该日期。

### 6.3 已完成任务

后续待办沿用现有“进行中 + 已完成折叠区”的结构：

- 进行中按日期分组；
- 已完成默认折叠；
- 已完成卡片必须显示其安排日期；
- 日期自然经过后，已完成任务不进入今日的“往日未完成”；
- 已完成历史仍可在原分组找到，第一版不建设计划归档页。

### 6.4 后续待办中的新建任务

后续待办没有单一上下文日期，因此新建区需要增加一个紧凑的日期字段：

```text
[所属分组] [任务标题                         ] [8月2日] [+]
```

规则：

- 默认日期为后天；
- 允许改为今天或未来日期；
- 保存后，任务进入对应的今日、明日或后续视图；
- 如果填写完成目标，目标日期必须与新任务安排日期一致；
- 移动端允许日期控件换到输入区第二行，不压缩任务标题到不可用宽度。

这使后续待办不仅能检查已有计划，也能直接建立未来计划。普通分组、今日和明日的新建流程保持不变。

## 7. 安排日期交互

### 7.1 轻量菜单

调整后的菜单：

```text
今天         7月31日                 ✓
明天         8月1日
────────────────────────
选择日期…    当前：8月15日
────────────────────────
取消安排     保留在原分组
```

规则：

- “今天”和“明天”仍然一键保存，不多一次确认；
- “选择日期…”打开独立对话框；
- 任务已安排到其他日期时，在该行显示格式化后的当前日期并显示选中标记；
- 任务没有安排时，副文案显示“今天及以后”；
- “取消安排”只清空日期，不改变分组、完成状态、目标或评价；
- 已安排到过去的任务，副文案显示“原安排：7月30日 · 已过期”。

不把完整月历直接展开在菜单中。现有菜单宽度小、同时服务桌面和移动端，内嵌月历会显著增加定位、键盘导航、视口避让和触屏尺寸复杂度。

### 7.2 自选日期对话框

第一版使用与现有目标/评价面板一致的原生日期输入：

```text
┌──────────────────────────────────────┐
│ 安排日期                          ×  │
│ 完成证书续费                         │
│ 子任务 · 父任务：网站运维            │
│                                      │
│ 处理日期                             │
│ [ 2026-08-15                     ]   │
│                                      │
│                         [取消] [保存] │
└──────────────────────────────────────┘
```

规则：

- 有可见标题和任务名称；
- 子任务显示父任务上下文；
- `min` 设置为打开面板时的本地今天；
- 不设置业务层最大日期；
- 新任务默认后天，已有未来日期默认当前值；
- 已过期任务默认今天，同时展示原安排日期；
- 保存前再次在 JavaScript 中校验，不能只依赖浏览器输入约束；
- `Escape` 或取消不修改数据，并把焦点返回原日历按钮；
- 保存成功后关闭面板，任务从当前不匹配的日期视图中移除；
- 保存失败时回滚乐观更新，保留输入值并展示云端错误。

### 7.3 保存后的反馈

提示文案：

| 结果 | Toast |
| --- | --- |
| 今天 | 已安排到今天 |
| 明天 | 已安排到明天 |
| 其他未来日期 | 已安排到 8月15日 |
| 清除 | 已取消日期安排 |

如果该日期没有完成目标，沿用当前行为，在日期保存成功后打开该日期的完成目标面板。任务的旧日期目标与评价不删除、不移动、不覆盖。

### 7.4 日历按钮状态

| 状态 | 可访问名称 | 视觉建议 |
| --- | --- | --- |
| 未安排 | 安排日期 | 现有低权重日历加号 |
| 今天 | 安排日期：今天 | 现有橙色选中态 |
| 明天 | 安排日期：明天 | 现有蓝色选中态 |
| 其他未来日期 | 安排日期：8月15日 | 通用已安排态，悬停/聚焦显示具体日期 |
| 已过期 | 安排日期：7月30日，已过期 | 通用已安排态加危险色小标记，颜色不是唯一提示 |

卡片操作区空间有限，第一版不在每张普通分组卡片上常驻完整日期文字；准确日期通过按钮的 `title`、`aria-label` 和安排菜单查看。后续待办卡片由于日期已经由分组标题表达，也不重复铺一枚日期标签。

## 8. 父任务与子任务规则

### 8.1 独立安排

以下状态都合法：

```text
父任务：8月5日；子任务 A：8月2日；子任务 B：未安排
父任务：未安排；子任务 A：8月10日
父任务和子任务 A：都安排在 8月3日
```

修改父任务日期时：

- 不修改任何子任务；
- 不询问是否批量同步；
- 不根据最早或最晚子任务日期推导父任务日期。

修改子任务日期时：

- 不修改父任务；
- 不修改兄弟子任务；
- 后续待办中继续显示父任务标题作为来源。

这是对现有今日/明日独立安排规则的自然延伸，也避免一次轻量操作产生隐式批量修改。

### 8.2 删除与移动分组

- 删除父任务仍级联删除子任务及其日期数据；
- 删除子任务只删除自身；
- 父任务移动分组时，已安排的父子任务仍出现在对应日期视图；
- 清除安排日期后，任务仍保留在原分组；
- 分组删除导致任务变为未分组时，不改变安排日期。

## 9. 日期与跨日规则

### 9.1 日期格式

`planned_date` 继续使用规范化的 `YYYY-MM-DD` 字符串，例如 `2026-08-15`。

- 表达用户本地日历日；
- 不构造成 UTC 零点再截取日期；
- 写入数据库 `date` 类型；
- 同一格式下可以安全进行日期相等和先后比较；
- 面向用户显示时再格式化为“8月15日 · 星期六”。

### 9.2 跨过午夜

应用现有的每分钟本地日期检查继续负责跨日刷新。日期变化后：

- 原今天的未完成任务成为往日未完成；
- 原明天任务进入今日待办；
- 后续待办中日期等于新明天的任务进入明日待办；
- 后续待办计数和日期分组同步更新；
- 已打开的日期选择面板更新最小合法日期；
- 用户已输入但尚未保存的昨日日期变为非法时，保存必须被阻止并提示重新选择。

### 9.3 往日未完成

继续沿用今日视图的“往日未完成”入口：

- 只包含未完成且 `planned_date < 今天` 的父任务和子任务；
- 可以单项或批量移到今天；
- 也可以通过安排菜单重新选择其他未来日期；
- 不自动把逾期任务推到今天；
- 不在“后续待办”重复展示逾期任务。

### 9.4 完成目标与完成评价

- 改变 `planned_date` 不改写任何目标日期；
- 改变 `planned_date` 不改写任何评价日期；
- 新日期缺少目标时，引导创建该日期目标；
- 未来日期不显示或创建完成评价；
- 当该日期到来后，今日视图按既有规则显示当日评价入口；
- 取消安排后，目标和评价历史仍可从任务入口查看。

## 10. 数据与技术方案

### 10.1 数据库

无需迁移。继续使用：

```sql
planned_date date
```

现有索引可以覆盖按用户和日期筛选：

```sql
create index if not exists todos_user_planned_date_idx
  on public.todos(user_id, planned_date)
  where planned_date is not null;
```

当前客户端会一次加载用户全部任务，再在内存中过滤；第一版沿用这一架构。若未来任务量明显增长，再把后续视图改为按日期范围查询，不在本次提前引入双数据源。

### 10.2 建议新增视图标识

```js
const LATER_CATEGORY_ID = 'later';
```

日期视图配置不应继续假设所有视图都能由固定 `offset` 表达。建议拆分：

```text
单日视图：today / tomorrow -> 精确 dateKey
范围视图：later -> plannedDate > tomorrowKey
普通视图：category / unassigned -> categoryId
```

避免给 `later` 伪造一个日期，否则完成目标投影、新建任务日期和标题都会得到错误上下文。

### 10.3 建议新增纯函数

```js
getLaterEntries(baseDate)
groupEntriesByPlannedDate(entries)
formatPlannedDateLabel(dateKey, baseDate)
isSelectablePlannedDate(dateKey, todayKey)
getPlannedDateToast(dateKey, baseDate)
```

这些函数应保持不依赖 DOM，便于覆盖月底、年底和闰日测试。

### 10.4 需要调整的模块

| 文件 | 主要变化 |
| --- | --- |
| `index.html` | 后续待办导航、选择日期菜单项、日期对话框、后续新建日期字段 |
| `js/main.js` | 范围视图、分组渲染、日期对话框、校验、Toast、跨日刷新与焦点管理 |
| `styles.css` | 后续导航、日期组标题、对话框和移动端输入布局 |
| `js/storage.js` | 原则上无需变化，只需继续传递任意合法 `plannedDate` |
| `supabase-schema.sql` | 无需变化 |
| `README.md` / `README_zh.md` | 实现后更新能力描述 |

### 10.5 保存与回滚

继续采用现有乐观更新：

```text
保存旧 plannedDate
    ↓
内存写入新日期并重绘
    ↓
更新 Supabase
    ├─ 成功：显示 Toast，按需打开完成目标面板
    └─ 失败：恢复旧日期并重绘，显示云端错误
```

如果修改日期后任务从当前视图消失，焦点返回策略应为：

1. 优先聚焦同一列表中下一项的日期按钮；
2. 没有下一项时聚焦上一项；
3. 列表为空时聚焦新建任务输入框；
4. 不尝试聚焦已经被重绘移除的旧按钮。

## 11. 无障碍与响应式要求

### 11.1 键盘

- 菜单继续支持上/下方向键、Home、End 和 Escape；
- “选择日期…”是正常 `menuitemradio` 或 `menuitem`，进入后焦点落在日期输入；
- 对话框关闭后焦点返回触发按钮，除非任务已离开当前视图；
- 日期输入有可见 `label`；
- 保存按钮在日期非法时禁用，并在提交时再次校验；
- 错误信息通过 `aria-live` 或现有 Toast 机制可被读出。

### 11.2 屏幕阅读器

建议名称示例：

```text
安排“完成证书续费”的日期
安排日期：8月15日
安排日期：7月30日，已过期
后续待办，7 项进行中
8月15日，星期六，4 项任务
```

日期组不能只靠颜色区分，必须有完整日期文字和任务数。

### 11.3 移动端

- 使用 `dialog` 和原生 `input[type="date"]`，不自行实现 7 列月历；
- 对话框宽度受视口约束，操作按钮不溢出；
- 后续日期组标题保持粘性不是第一版要求；
- 新建区的日期字段在窄屏换行，不缩小字体或挤压添加按钮；
- 触控目标保持与现有菜单按钮一致的最小高度。

## 12. 方案取舍

### 12.1 方案 A：只在现有菜单增加日期输入

优点：实现量最小。

缺点：

- 后天任务没有聚合入口；
- 用户必须记得任务原分组；
- 无法检查未来负载；
- 功能可写入但不可管理。

结论：不采用。

### 12.2 方案 B：每个未来日期增加一个侧栏入口

优点：日期直接可见。

缺点：

- 侧栏会随计划日期数量无限增长；
- 与自定义分组竞争空间；
- 移动端抽屉扫描成本高；
- 空日期和跨月导航难处理。

结论：不采用。

### 12.3 方案 C：完整月历/周历

优点：未来计划的全局感最强，适合拖拽排期。

缺点：

- 与当前列表型产品结构差异过大；
- 需要月历键盘模型、日期格状态、跨月和移动端布局；
- 用户当前需求只是选择其他日期；
- 会把提醒、时刻和负载管理等新需求提前带入。

结论：不进入第一版，可作为未来独立项目评估。

### 12.4 方案 D：快捷菜单 + 日期对话框 + 后续待办

优点：

- 高频操作仍然一步完成；
- 任意未来日期有稳定入口承接；
- 与当前原生日期控件和列表渲染方式一致；
- 不修改数据结构；
- 桌面和移动端都可控。

结论：推荐。

## 14. 验收标准

### 14.1 核心行为

1. 父任务可以安排到后天及更远日期。
2. 子任务可以独立安排到后天及更远日期。
3. 今天和明天仍可从菜单一键安排。
4. 不能保存过去日期。
5. 其他未来日期保存后显示准确日期 Toast。
6. 后天及更远的未完成任务出现在后续待办，并按日期升序分组。
7. 父任务与子任务同日安排时各自出现，不合并、不去重。
8. 修改父任务日期不修改子任务，反之亦然。
9. 清除安排只清空 `planned_date`。
10. 修改安排日期不删除或迁移完成目标、完成评价。

### 14.2 日期变化

11. 跨过午夜后，原明日任务进入今日待办。
12. 跨过午夜后，原后天任务进入明日待办。
13. 过期未完成任务只进入今日的往日未完成区，不出现在后续待办。
14. 月末、年末和闰日切换结果正确。
15. 不同系统时区下，数据库日期与用户选择的日历日一致。

### 14.3 视图与交互

16. 后续待办计数只统计未完成任务，父子任务口径与今日/明日一致。
17. 后续待办空状态明确提示通过任务日历按钮选择未来日期。
18. 后续待办新建任务必须有明确安排日期，完成目标使用同一日期。
19. 在当前日期视图修改日期后，任务立即从不匹配的视图移除。
20. 云端保存失败时恢复原日期，任务不丢失。
21. Realtime 收到其他设备的日期更新后，三个日期导航计数与当前列表一致。

### 14.4 无障碍与响应式

22. 菜单和对话框可以只用键盘完成操作。
23. Escape、取消和保存后的焦点位置合理，不落到已移除节点。
24. 屏幕阅读器能读出任务名、具体日期和过期状态。
25. 360px、390px、430px 移动端宽度下，菜单、对话框、新建区和日期组标题无重叠或横向溢出。
26. 关闭动画偏好下不依赖动画表达状态变化。

## 17. 最终决策摘要

```text
是否合理：合理
实现前提：必须同时提供未来任务找回入口
日期范围：今天及未来，不主动安排到过去
交互：今天 / 明天快捷项 + 选择日期对话框
导航：新增后续待办，展示后天及更远日期
列表：按 planned_date 升序分组
父子关系：独立安排，不级联
数据结构：复用 todos.planned_date，无数据库迁移
第一版排除：时刻、提醒、重复、自然语言、完整日历
```
