# 按日期记录的今日复盘设计方案

> 文档状态：产品、交互与数据方案已收敛，可作为后续实现依据
> 最后更新：2026-08-01
> 前置功能：`docs/completion-goal-design.md` 的按日期完成目标、`docs/daily-completion-review-design.md` 的任务级每日完成评价

## 1. 一句话定义

“今日复盘”是用户针对某个本地日历日保存的一条工作记录，用来回答：

> 今天实际把时间和精力用在哪里？计划为什么发生了变化？我从中发现了什么？

它不是任务的完成状态，也不是任务评价的汇总，而是工作日层面的上下文记录。

示例：

```text
8月1日今日复盘

上午完成了移动端列表的 390px 布局。下午原本准备修复 430px 溢出，
但先去研究了新的拖拽交互，发现还需要先整理任务排序的数据结构。
另外临时处理了一次线上登录问题。明天先完成排序数据结构，再继续按钮溢出修复。
```

## 2. 结论与合理性评估

这个需求合理，建议实现。它补上了当前任务模型没有覆盖的一层事实：

```text
今日完成目标：今天准备把某个任务推进到哪里？
今日完成评价：某个任务今天实际推进得怎么样？
今日复盘：今天整个工作日实际上发生了什么？
```

用户描述的三种情况都属于日级信息：

| 情况 | 为什么不适合只写在任务评价里 |
| --- | --- |
| 临时插入其他事情 | 临时事情可能没有对应任务，或者涉及多个任务 |
| 因好奇心探索其他方向 | 探索本身可能暂时没有明确的任务结果，但对当天决策有价值 |
| 发现前置任务或依赖 | 它解释了原任务为什么没有按计划推进，通常会影响多个后续任务 |

记录这类信息有三个直接价值：

1. 让“任务未完成”不再等同于“今天没有产出”；
2. 让次日计划建立在真实原因上，而不是凭记忆重新猜测；
3. 逐步识别反复出现的打断、估时偏差和隐性前置工作。

但它也有一个边界：如果把它做成强制的长表单，用户会把复盘当成另一项待办，反而增加负担。因此第一版应当“可选、快速、以正文为主”。

## 3. 产品概念与命名

### 3.1 推荐名称

界面统一使用 **今日复盘**。数据表和代码使用 `daily_reviews`。

不推荐第一版使用“日记”作为主名称：

- “日记”容易让用户期待情绪、生活和私密记录等更宽泛的能力；
- 当前功能的直接目的，是帮助回顾工作计划和实际偏差；
- “今日复盘”与已有“今日完成评价”语义相邻，用户更容易理解入口位置。

正文可以在提示语中使用“记录”或“写下今天发生了什么”，保留日记式的自由度。

### 3.2 与现有功能的边界

| 概念 | 所属范围 | 回答的问题 | 是否影响任务状态 |
| --- | --- | --- | --- |
| 今日完成目标 | 单个父任务或子任务 | 今天准备推进到哪里？ | 否 |
| 今日完成评价 | 单个父任务或子任务、按日期 | 这个任务今天实际推进得怎么样？ | 否 |
| 今日复盘 | 用户、按日期 | 今天整体发生了什么、为什么变化？ | 否 |
| 任务描述 | 单个任务 | 背景、资料和长期注意事项是什么？ | 否 |

任务级评价仍然保留 `已达成 / 部分达成 / 未推进` 三档和目标快照；今日复盘不复制这些内容，也不从它们自动汇总正文。

## 4. 信息架构

用户的每日记录关系如下：

```text
用户
└─ 今日复盘历史
   ├─ 2026-07-30
   ├─ 2026-07-31
   └─ 2026-08-01
```

它与任务是并列关系，而不是任务的子记录：

```text
今日复盘（8月1日）
├─ 可提到任务 A 的实际进展
├─ 可提到临时事务 B
├─ 可提到探索方向 C
└─ 可提到任务 D 的前置依赖
```

同一天只保存一条记录。用户再次打开并保存时更新当天记录，而不是产生一条新的版本。第一版不做逐次编辑的版本历史。

## 5. 第一版内容模型

### 5.1 推荐采用一段正文

编辑面板使用一个自由文本框，最多 3000 个字符。输入框通过提示语引导用户覆盖四类信息，但不把四类信息做成四个必填字段：

```text
今天实际推进或完成了什么？
有哪些临时事务、计划外探索或打断？
发现了哪些阻塞、前置任务或依赖？
明天准备继续、调整或放弃什么？
```

这样做的理由：

- 用户可以只写一句“处理了线上问题，主任务顺延”，不会被表单阻塞；
- 复杂的一天仍可写成完整叙述；
- 不需要预先判断一条内容属于“总结”“反思”还是“日记”；
- 数据结构简单，后续增加标签或统计时仍可兼容。

### 5.2 保存条件

- 记录本身是可选的，用户可以不写；
- 新建或更新时，正文去除首尾空白后必须至少有 1 个字符；
- 正文上限 3000 个字符，前端计数并在保存时再次校验；
- 删除当天复盘后，该日期恢复为“尚未记录”；
- 空白正文不写入数据库，不创建空记录。

### 5.3 为什么暂不拆成多个字段

“临时事务”“探索”“依赖”“明日计划”确实可以结构化，但第一版拆成多个字段会带来三个问题：

1. 每天打开后需要面对更多输入项；
2. 用户会为了填满字段而编造不重要的内容；
3. 结构化字段尚未有对应的筛选、统计或提醒能力。

后续如果数据证明用户反复记录同一类偏移原因，再增加可选标签或单独字段，而不是一开始就增加负担。

## 6. 入口与页面布局

### 6.1 今日视图入口

只在“今日待办”工作区提供显眼入口，不在每张任务卡片上重复显示。

入口位于工作区标题和任务列表之间，复用现有工作区样式，采用紧凑的无边框横条：

```text
今日待办
3 项进行中 · 2 项已完成

今日复盘 · 尚未记录                         写今日复盘
```

已有记录时显示更新时间和最多两行摘要：

```text
今日复盘 · 已更新 18:40                     编辑
处理登录问题；发现排序结构是移动端修复的前置工作……
```

不把完整正文长期铺在任务列表中，避免今日任务被日志内容淹没。移动端保持同样顺序，按钮使用图标加文字，触控高度不少于 40px。

### 6.2 编辑面板

点击“写今日复盘”“编辑”或摘要区域，打开现有 `<dialog>` 视觉体系中的 `daily-review-dialog`：

```text
┌──────────────────────────────────────┐
│ 今日复盘                         ×   │
│ 2026年8月1日                         │
│                                      │
│ [今天实际推进或完成了什么？           │
│  有哪些临时事务、探索或打断？          │
│  发现了哪些阻塞或前置任务？             │
│  明天准备继续或调整什么？             ] │
│                                      │
│ 0/3000                                │
│ 历史复盘 5                            │
│                                      │
│                 删除    保存复盘      │
└──────────────────────────────────────┘
```

规则：

- 日期显示为只读的今天；历史记录通过历史列表选择，不在主入口中修改日期；
- 首次打开时聚焦文本框；
- 保存按钮固定在底部，关闭时未保存内容不自动覆盖已有记录；
- 删除已有记录必须二次确认；
- 保存成功后关闭面板并刷新入口摘要；
- 保存失败时保留输入内容并展示错误，不关闭面板。

### 6.3 历史记录

编辑面板内提供默认折叠的“历史复盘 N”入口。展开后按日期倒序显示，每项包含日期、更新时间和正文摘要；点击历史项后在同一面板中编辑该日期。

历史规则：

- 默认先显示最近 5 条；
- 超过 5 条显示“加载更多”，每次增加 5 条；
- 历史正文不在今日任务卡片中平铺；
- 没有历史时不显示空的时间线，只显示“还没有复盘记录”；
- 历史编辑只能选择今天或过去日期，不能创建未来复盘。

第一版不增加独立的“日历页”或侧栏中的每天入口，避免导航层级膨胀。通过今日入口进入历史即可满足回顾需求。

## 7. 典型使用流程

### 7.1 日中快速记录

1. 用户在今日待办中点击“写今日复盘”；
2. 写下一两句当前发生的变化；
3. 点击保存，继续处理任务。

复盘可以在一天中多次更新，但数据库仍然只有当天一条记录，更新时间反映最后一次保存。

### 7.2 日终复盘

1. 用户完成或暂停当天工作；
2. 从今日待办顶部打开已有复盘或创建复盘；
3. 对照任务级目标和评价，补充计划外事项、阻塞原因和明日调整；
4. 保存后退出，不要求逐个任务都填写评价。

### 7.3 回顾过去

1. 打开今日复盘入口；
2. 展开“历史复盘”；
3. 选择日期阅读或编辑；
4. 保存后仍回到原来的历史位置。

## 8. 日期、跨日与删除规则

### 8.1 日期语义

- `review_date` 使用用户设备的本地日历日，格式为 `YYYY-MM-DD`；
- 今日入口只操作当前本地日期；
- 可以补录今天和过去日期；
- 不能保存未来日期的复盘；
- 客户端日期变化时刷新入口日期、摘要和历史列表。

数据库不使用依赖服务器时区的“不能晚于今天”检查。未来日期限制由客户端按本地日历日执行，并在保存函数中再次校验。

### 8.2 跨日

- 到第二天后，昨天的复盘保留在历史中；
- 系统不自动创建、修改或删除任何复盘；
- 不因为昨日任务未完成而自动生成复盘正文；
- 今天首次进入时仍显示“尚未记录”，由用户主动决定是否填写。

这与任务级完成评价不同：完成评价可以根据明确的安排事实自动补记“未推进”，日级复盘不能由任务状态推断出用户当天的真实经历。

### 8.3 任务操作的影响

- 移动任务日期、取消安排、完成或重新打开任务，都不影响日级复盘；
- 删除任务不会删除任何日级复盘；
- 删除账号时通过 `user_id` 外键级联删除该用户的复盘历史。

## 9. 数据库设计

### 9.1 新表

建议在 `supabase-schema.sql` 中新增 `public.daily_reviews`：

```sql
create table if not exists public.daily_reviews (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  review_date date not null,
  content text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint daily_reviews_content_check check (
    length(trim(content)) between 1 and 3000
  ),
  constraint daily_reviews_one_per_day unique (user_id, review_date)
);
```

### 9.2 索引、更新时间和权限

- 增加 `(user_id, review_date desc)` 索引；
- 复用现有 `set_*_updated_at` trigger 模式更新 `updated_at`；
- 开启 RLS；
- 只授予 authenticated 用户 select、insert、update、delete；
- 所有策略都限制 `user_id = auth.uid()`；
- 如启用 Supabase Realtime，将表加入现有私有用户频道。

### 9.3 客户端映射

`storage.js` 增加：

- `dailyReviews` 内存集合；
- `mapDailyReviewRow`；
- `loadDailyReviews`；
- `upsertDailyReviewRecord`；
- `deleteDailyReviewRecord`。

加载任务时并行加载日级复盘，但不要把复盘挂载到每个 todo 对象上；它属于用户和日期，应通过 `getDailyReviewForDate(dateKey)` 查询，避免造成父子任务数据重复。

`main.js` 增加：

- 当前日期入口摘要渲染；
- 编辑 dialog 状态和保存流程；
- 历史列表渲染；
- Realtime 更新后的局部刷新；
- 登出、切换账号和重新加载时的状态清理。

## 10. 与任务级复盘的协作规则

两类复盘允许互相提及，但不自动复制：

```text
任务 A 的今日完成评价：
部分达成，完成了接口联调，权限问题待处理。

8月1日今日复盘：
接口联调有推进；权限问题暴露出鉴权前置任务，明天先补齐它。
```

明确不做：

- 不从任务评价自动拼接每日复盘正文；
- 不从每日复盘推断任务的达成结果；
- 不因为每日复盘存在而改变任务完成状态、完成率或子任务进度；
- 不要求任务评价和每日复盘成对存在；
- 不在每日复盘中复制任务目标快照。

## 11. Realtime 与并发规则

- 同一账号在多个设备打开时，新增、更新和删除日级复盘应实时同步；
- 如果编辑面板打开期间收到其他设备更新，保留当前输入，不静默覆盖；
- 可以在面板顶部提示“记录已在其他设备更新”，由用户选择重新载入或继续保存；
- 保存使用 `(user_id, review_date)` 唯一约束和 upsert，避免同一天产生重复记录；
- 第一版不提供冲突合并或逐段 diff。

## 12. 实施顺序

### 阶段一：数据层

1. 新增 `daily_reviews` 表、约束、索引、trigger、RLS 和 Realtime 配置；
2. 在 `storage.js` 中增加加载、upsert、删除和映射；
3. 增加账号切换时的内存状态清理。

### 阶段二：编辑面板

1. 增加 `daily-review-dialog` HTML；
2. 实现正文校验、字符计数、新增、更新、删除；
3. 实现历史折叠和历史项编辑；
4. 处理关闭、错误、焦点返回和移动端布局。

### 阶段三：今日工作区入口

1. 在今日工作区标题下增加复盘横条；
2. 显示未记录、已更新和摘要三种状态；
3. 保存或 Realtime 更新后只刷新横条，不重绘整个任务树；
4. 明日待办、后续待办和普通分组不显示今日复盘正文入口。

### 阶段四：验证

1. 新用户、已有用户和空数据升级路径；
2. 今天、过去、未来日期限制；
3. 同日 upsert、删除和跨设备更新；
4. 长文本、六套主题、窄屏和键盘焦点；
5. 确认任务完成状态、任务评价、目标和完成率均不受影响。

## 13. 验收标准

### 13.1 产品行为

- 用户可以在今日待办中创建今日复盘；
- 一天最多一条记录，重复保存会更新原记录；
- 正文长度在 1 到 3000 个字符之间；
- 删除后当天显示为尚未记录；
- 可以从历史列表查看和编辑过去记录；
- 不能创建未来记录；
- 跨日不会自动生成或删除复盘；
- 临时事务、探索和前置依赖可以在同一段正文中被记录。

### 13.2 显示与交互

- 今日入口在任务列表附近可见，但不占用任务卡片正文区域；
- 已有记录显示更新时间和不超过两行的摘要；
- 历史默认折叠，按日期倒序；
- 保存失败时输入内容不丢失；
- 关闭 dialog 后焦点返回打开入口；
- 移动端无横向溢出，文本和按钮不重叠。

### 13.3 数据与非回归

- 不同用户只能读写自己的复盘；
- 删除账号会级联删除复盘；
- 删除任务不会删除复盘；
- 任务级完成目标和完成评价保持原有历史；
- 今日复盘不改变任务完成状态、完成率、任务数量和子任务进度；
- 多设备更新最终显示一致。

## 14. 第一版明确不做

- 自动根据任务状态生成复盘；
- 强制日终弹窗、浏览器通知或未填写惩罚；
- 四个字段全部必填的日终表单；
- 情绪、精力、工时和专注度评分；
- 百分比、星级或质量评分；
- 自动识别临时事务、探索和阻塞原因；
- AI 总结、任务评价汇总或自动生成明日计划；
- 评论、附件、多人协作和逐次编辑版本历史；
- 独立周报/月报页面和复杂日历视图。

## 15. 后续演进方向

只有在积累真实使用数据后再考虑以下能力：

1. 可选的偏移原因标签：临时事务、探索、前置依赖、估时偏差、精力不足、其他；
2. “最近 7 天复盘”摘要，帮助发现重复阻塞；
3. 从今日复盘一键生成明日待办草稿，但必须由用户确认；
4. 任务级评价与日级复盘之间的手动引用，而不是自动拼接；
5. 本地草稿恢复，减少移动端误关闭造成的输入损失。

演进的前提是先确认用户真的愿意持续写复盘。第一版的成功标准不是记录字段更多，而是用户能在一分钟内留下有用的当天上下文。

## 16. 方案摘要

```text
产品名称：今日复盘
记录粒度：用户 × 本地日历日
核心内容：一段自由正文，提示覆盖实际进展、计划外事项、阻塞依赖、明日调整
保存策略：每天最多一条，显式保存，允许更新和删除
历史策略：按日期保留，默认折叠，不创建逐次版本
未来日期：禁止
与任务的关系：并列，不继承、不汇总、不改变任务状态
第一版入口：今日待办工作区顶部紧凑横条 + dialog
第一版数据表：public.daily_reviews
```
