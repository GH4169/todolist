# 按日期记录的每日完成评价设计方案

> 文档状态：产品、交互与数据方案已收敛，可直接作为后续实现依据  
> 最后更新：2026-07-31  
> 前置功能：`docs/completion-goal-design.md` 中的“按日期完成目标”已实现  
> 适用范围：父任务、子任务、今日待办、往日补录、普通分组中的历史入口

## 1. 一句话定义

“每日完成评价”是任务自身拥有的一组、按日期保存的每日复盘记录，用来回答：

> 这一天原本准备推进到哪里，实际推进到了哪里，结果属于达成、部分达成还是未达成？

它与“完成目标”共同构成一条完整的每日推进链路：

```text
事前计划：今日完成目标
       ↓
当天执行：父任务或子任务持续推进
       ↓
事后复盘：今日完成评价
```

示例：

```text
任务：完成移动端重构

7月31日完成目标：
完成任务列表布局，并检查 390px 与 430px 两种尺寸

7月31日完成评价：部分达成
已完成 390px 布局；430px 下操作按钮仍有溢出，明天继续修复
```

整个任务此时仍然可以是“未完成”。每日评价描述的是某一天的推进结果，不等同于整个任务的完成状态。

## 2. 已确认的需求理解

### 2.1 父任务和子任务都能独立评价

- 父任务可以评价当天整体推进结果。
- 每个子任务可以评价自己的当天推进结果。
- 父任务评价不自动汇总子任务评价。
- 子任务评价不自动改变父任务评价。
- 父任务与子任务即使安排在同一天，也各自保存独立记录。

### 2.2 评价必须绑定日期

每条评价至少包含：

- 所属任务；
- 评价日期；
- 达成结果；
- 实际完成情况；
- 当时完成目标的文字快照；
- 创建时间；
- 最后修改时间。

一个任务可以跨越多天，每一天最多拥有一条评价。

### 2.3 评价与任务完成状态分离

以下情况都合法：

```text
今日目标已达成 + 整个任务未完成
今日目标部分达成 + 整个任务未完成
今日目标未达成 + 整个任务后来被标记完成
今日没有设目标 + 仍补录了实际完成情况
```

评价不会自动勾选任务，也不会自动重新打开任务。

### 2.4 评价以当天目标为参照，但不依赖目标存在

- 当天存在完成目标时，评价面板展示该目标，并在保存评价时复制一份目标文字快照。
- 当天没有完成目标时，仍允许评价，面板明确显示“当天未设完成目标”。
- 不因为缺少目标而阻断复盘。
- 不自动为缺少目标的日期补建一条完成目标。

### 2.5 旧评价始终保留

- 任务从今天移动到明天后，今天的评价继续保留。
- 取消任务安排日期不会删除评价。
- 任务完成、重新打开或移动分组不会删除评价。
- 删除任务时，通过数据库外键级联删除该任务的目标和评价历史。

## 3. 产品概念与命名

推荐统一使用以下名称：

| 概念 | 界面文案 | 回答的问题 |
| --- | --- | --- |
| 日期计划 | 今日完成目标 | 今天准备推进到哪里？ |
| 日期复盘 | 今日完成评价 | 今天实际推进得怎么样？ |
| 结构化结果 | 达成结果 | 达成、部分达成还是未达成？ |
| 复盘正文 | 实际完成情况 | 实际做到了什么，剩余什么？ |
| 整体状态 | 任务完成状态 | 整个任务是否结束？ |

不推荐把评价命名为“完成程度”，因为它容易与百分比进度、子任务数量和已有完成目标混淆。

## 4. 达成结果的固定枚举

第一版只使用三档，不增加数字评分：

| 数据值 | 界面文案 | 含义 |
| --- | --- | --- |
| `achieved` | 已达成 | 当天目标的关键边界已经达到 |
| `partial` | 部分达成 | 有实质推进，但没有达到完整边界 |
| `missed` | 未达成 | 没有形成目标要求的有效结果 |

### 4.1 为什么不使用百分比

- `70%` 的判断标准不稳定，不同任务之间不可比较。
- 它会与现有子任务 `2/5`、顶部完成率竞争。
- 每日复盘的核心是确认是否越过当天设定的边界，而不是制造精确但虚假的数字。

### 4.2 为什么正文仍然必填

结构化结果便于快速扫描，实际完成情况则保存事实。第一版规定：

- 达成结果必选；
- 实际完成情况必填；
- 正文长度为 1–500 字符；
- 即使选择“已达成”，也要简要写明实际产出，而不是只保存一个绿色标签。

这保证评价记录不仅能统计，还能在以后重新阅读时提供有效信息。

## 5. 信息架构

### 5.1 任务的日期推进记录

```text
任务
├─ 基本信息
│  ├─ 标题
│  ├─ 描述
│  ├─ 当前安排日期
│  └─ 整体完成状态
├─ 多条按日期完成目标
│  ├─ 7月30日目标
│  ├─ 7月31日目标
│  └─ 8月1日目标
└─ 多条按日期完成评价
   ├─ 7月30日评价
   ├─ 7月31日评价
   └─ 8月1日评价
```

目标与评价是两个独立的一对多关系，共同通过 `todo_id` 归属于具体任务。

### 5.2 目标快照

评价保存时，应把该日期当前的完成目标文字复制到评价记录的 `goal_content_snapshot`。

原因：

- 用户可能在评价后继续修改当天目标；
- 用户可能删除当天目标；
- 历史评价必须说明当时对照的目标是什么；
- 不能让事后修改计划悄悄改变过去复盘的语义。

规则：

- 当天有目标：保存当前目标文字快照。
- 当天无目标：快照为 `NULL`。
- 编辑已有评价时，默认保留原快照。
- 如果用户改变评价日期，则使用新日期当前的目标重新生成快照。
- 第一版不提供手动编辑目标快照。

## 6. 日期规则

### 6.1 每个任务每天最多一条评价

- 同一天再次保存：更新已有评价。
- 新日期保存：新增评价。
- 不记录同一天每次编辑的版本历史。
- 数据库通过 `unique (todo_id, review_date)` 保证唯一。

### 6.2 不能评价未来日期

- 今日和往日可以评价。
- 明天及更远日期不能提前评价。
- 明日待办只展示明日完成目标，不展示“明日完成评价”入口。
- 客户端日期输入设置 `max = 今天` 并在保存时再次校验。

数据库不使用 `review_date <= current_date` 检查，因为服务器日期与用户本地日期可能受时区影响。日期合法性按现有 `planned_date` 的本地日历语义由客户端控制。

### 6.3 补录往日评价

允许用户为过去日期补录评价：

- 从评价面板修改日期；
- 从历史列表选择已有评价编辑；
- 普通分组任务操作入口默认打开今天，用户可切换到往日。

不会自动为所有过期目标生成“未达成”评价，因为没有填写评价不等于未达成。

## 7. 卡片显示规则

### 7.1 今日待办

今日卡片形成明确的“计划—复盘”上下结构：

```text
┌──────────────────────────────────────────┐
│ □ 完成移动端重构                    ···  │
│                                          │
│ │ 今日完成目标                           │
│ │ 完成任务列表布局，并检查两种尺寸       │
│                                          │
│ ✓ 今日完成评价 · 部分达成                │
│   已完成 390px，430px 仍有按钮溢出       │
│                                          │
│ 产品开发 · 子任务 2/5                   │
└──────────────────────────────────────────┘
```

规则：

1. 标题；
2. 今日完成目标；
3. 今日完成评价；
4. 分组、时间和子任务进度；
5. 操作按钮。

### 7.2 今日尚未评价

未评价状态展示轻量入口：

```text
○ 评价今日完成情况
  写下实际做到哪里
```

- 入口必须可见，但视觉权重低于目标正文。
- 不使用警告色，不暗示用户做错了什么。
- 已完成任务仍显示该入口，因为“勾选完成”和“填写复盘”是两件事。

### 7.3 今日已有评价

卡片最多显示一条当天评价：

- 显示结果标签；
- 实际完成情况最多两行；
- 点击整个评价区域进入编辑面板；
- 不在卡片平铺往日评价。

状态视觉：

| 结果 | 色彩语义 | 说明 |
| --- | --- | --- |
| 已达成 | 现有绿色 | 表示当天边界已越过 |
| 部分达成 | 现有今日橙 | 表示仍在推进中 |
| 未达成 | 现有粉红/危险色 | 表示需要重新规划，不代表失败惩罚 |

颜色不能作为唯一信息来源，始终显示文字标签。

### 7.4 明日待办

- 不展示评价块。
- 不允许提前评价未来结果。
- 继续只展示“明日完成目标”。

### 7.5 普通分组

普通分组默认不在任务树内展示最新评价正文，避免父子树同时出现目标和评价后过于拥挤。

第一版采用：

- 卡片仍按现有规则显示最新完成目标；
- 父任务和子任务操作区增加“完成评价”入口；
- 已存在今日评价时，入口可使用状态色轻量标记；
- 点击后进入评价面板，可查看历史。

这是对原设想的收敛：评价正文只在最需要日终复盘的今日视图展开，历史能力则在所有任务上下文中可达。

### 7.6 今日的独立子任务

独立安排到今天的子任务与父任务使用相同规则：

```text
子任务
□ 适配任务列表

今日完成目标
完成列表布局并检查长文本

今日完成评价 · 已达成
两种宽度和长标题场景均已检查

来自：完成移动端重构 · 产品开发
```

不展示或继承父任务的目标和评价。

## 8. 评价编辑面板

### 8.1 打开方式

- 点击今日卡片上的“评价今日完成情况”；
- 点击已有的今日评价；
- 点击父任务操作区的“完成评价”图标；
- 点击子任务操作区的“完成评价”图标；
- 在历史列表中选择某一日期的评价。

### 8.2 桌面端结构

继续复用现有 `<dialog>` 视觉体系，宽度约 `540px`：

```text
┌────────────────────────────────────────────┐
│ 每日复盘                             ×     │
│ 完成移动端重构                             │
│                                            │
│ 评价日期                                   │
│ [ 2026-07-31 ]                             │
│                                            │
│ 当天完成目标                               │
│ 完成任务列表布局，并检查两种尺寸           │
│                                            │
│ 达成结果                                   │
│ [ 已达成 ] [ 部分达成 ] [ 未达成 ]         │
│                                            │
│ 实际完成情况                               │
│ [ 已完成 390px，430px 仍有按钮溢出…… ]    │
│                                            │
│ ▸ 历史评价 3                               │
│                                            │
│                       取消   保存评价       │
└────────────────────────────────────────────┘
```

### 8.3 当天目标对照区

- 有当天目标：显示目标全文。
- 没有当天目标：显示“当天未设完成目标，可以直接记录实际完成情况”。
- 目标区只读。
- 提供“编辑当天目标”链接可打开现有完成目标面板；第一版可在关闭评价面板后再打开目标面板，避免嵌套 dialog。

### 8.4 达成结果选择

使用原生 radio 语义，视觉为三段选择按钮：

```html
<fieldset>
  <legend>达成结果</legend>
  <label><input type="radio" name="review-result" value="achieved">已达成</label>
  <label><input type="radio" name="review-result" value="partial">部分达成</label>
  <label><input type="radio" name="review-result" value="missed">未达成</label>
</fieldset>
```

- 不默认替用户选择结果。
- 编辑已有评价时恢复原选择。
- 键盘可以通过方向键切换。
- 可访问名称不能只依赖图标或颜色。

### 8.5 历史评价

历史区域默认折叠，按评价日期倒序：

```text
⌄ 历史评价 3

7月31日 · 部分达成
已完成 390px，430px 仍有按钮溢出

7月30日 · 已达成
完成首页结构和桌面端布局
```

每条历史展示：

- 日期；
- 结构化结果；
- 实际完成情况；
- 目标快照摘要；
- 当前正在编辑的记录标记“当前”。

默认展示最近 5 条，更多记录通过“查看更多”加载。

### 8.6 编辑和删除

- 可以编辑任意日期的评价。
- 可以删除任意一条评价，需要二次确认。
- 修改评价日期产生冲突时，不静默覆盖。
- 用户明确确认后，使用当前内容替换目标日期已有评价，并删除原日期记录。
- 删除评价不删除目标、不删除任务、不改变任务完成状态。

### 8.7 移动端

- 第一版继续使用响应式居中 dialog。
- 宽度接近视口，高度不超过视口。
- 内容区域内部滚动。
- 保存操作固定在底部。
- 三档结果在窄屏仍保持一行；极窄屏可改为三行，但每项触控高度至少 40px。

## 9. 日终提醒与填写时机

第一版不根据时间自动弹窗，也不在某个固定时刻强制提醒。

原因：

- 不同用户的工作结束时间不同；
- 浏览器静态应用没有可靠的后台提醒机制；
- 自动弹窗会打断仍在工作的用户；
- 评价入口始终可见已经能支持日终使用。

后续可以独立验证：

- 用户可配置的日终提醒时间；
- 今日视图顶部“还有 N 项未评价”的汇总；
- 一次连续评价今日所有任务的复盘模式。

这些都不进入第一版实现范围。

## 10. 日期变化和顺延规则

### 10.1 今天移动到明天

- 今天完成目标保留。
- 今天完成评价保留（如果已经填写）。
- 如果今天尚未评价，不自动创建“未达成”。
- 明天到来前不允许填写明天评价。
- 明天仍按现有逻辑补写明日完成目标。

### 10.2 往日未完成移动到今天

- 往日目标和评价都保留。
- 今日卡片显示今日目标或最近过去目标。
- 今日评价入口只对应今天。
- 用户如需补录往日评价，通过面板日期选择完成。

### 10.3 取消安排日期

- 只清空 `planned_date`。
- 所有目标和评价历史保留。
- 普通分组中仍可通过任务操作进入评价历史。

### 10.4 任务完成

- 勾选完成不自动生成“已达成”评价。
- 今日已完成卡片仍可填写评价。
- 评价结果不会被任务完成状态覆盖。
- 清除或删除已完成任务时，其评价随任务级联删除。

## 11. 数据库设计

### 11.1 新表

推荐新增独立表：

```sql
create table if not exists public.todo_completion_reviews (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid()
    references auth.users(id) on delete cascade,
  todo_id uuid not null,
  review_date date not null,
  result text not null
    check (result in ('achieved', 'partial', 'missed')),
  content text not null
    check (length(trim(content)) between 1 and 500),
  goal_content_snapshot text
    check (
      goal_content_snapshot is null
      or length(trim(goal_content_snapshot)) between 1 and 500
    ),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint todo_completion_reviews_todo_owner_fkey
    foreign key (todo_id, user_id)
    references public.todos(id, user_id)
    on delete cascade,

  constraint todo_completion_reviews_one_per_day
    unique (todo_id, review_date)
);
```

索引：

```sql
create index if not exists todo_completion_reviews_user_todo_date_idx
  on public.todo_completion_reviews(user_id, todo_id, review_date desc);
```

还需沿用现有项目的：

- `updated_at` trigger；
- authenticated 表权限；
- 按 `user_id = auth.uid()` 的四类 RLS policy；
- 私有 Realtime Broadcast；
- 从 `supabase_realtime` publication 中移除；
- 删除任务时数据库级联删除。

### 11.2 为什么使用独立表

不把评价字段直接放进 `todo_completion_goals`：

- 没有目标的日期仍允许评价；
- 目标和评价的创建、编辑时间不同；
- 目标可能被删除，但评价需要保留目标快照；
- 两类记录的权限虽然相同，业务生命周期不同；
- 独立表更清晰地表达“计划事实”和“复盘事实”。

### 11.3 为什么不保存评分数字

第一版只保存固定枚举 `result`。如果未来需要统计，可直接计算三类数量和比例，不需要提前引入主观分数。

## 12. 客户端模型

父任务与子任务都扩展为：

```js
{
  id,
  text,
  plannedDate,
  completionGoals: [/* 已有 */],
  completionReviews: [
    {
      id,
      userId,
      todoId,
      reviewDate: '2026-07-31',
      result: 'partial',
      content: '已完成 390px，430px 仍有按钮溢出',
      goalContentSnapshot: '完成任务列表布局，并检查两种尺寸',
      createdAt,
      updatedAt,
    },
  ],
}
```

评价数组统一按：

```text
reviewDate DESC, updatedAt DESC
```

排序。

### 13.2 加载流程

`loadTodos()` 可将目标和评价与 todos 查询并行加载：

```js
const [todoResult, goals, reviews] = await Promise.all([
  loadTodoRows(),
  loadCompletionGoals(),
  loadCompletionReviews(),
]);

assembleParentChildTodos();
attachCompletionGoals(todos, goals);
attachCompletionReviews(todos, reviews);
```

每个父任务和子任务必须始终包含空数组默认值，避免渲染时判断 `undefined`。

### 13.3 Realtime

独立 topic：

```text
todo-completion-reviews:{userId}
```

第一版可以继续沿用当前“收到目标或分组变化后短延迟重新加载”的策略，保证正确性；后续再优化为局部更新。

评价变化后：

- 重新挂载父子任务评价数组；
- 重绘今日列表和受影响任务；
- 如果评价 dialog 正在打开，保持当前日期和历史展开状态；
- 不重新计算任务完成率、任务计数和子任务进度。

## 14. 核心业务算法

### 14.1 取某日评价

```js
function getCompletionReviewForDate(item, reviewDate) {
  return item.completionReviews.find(review => (
    review.reviewDate === reviewDate
  )) || null;
}
```

今日卡片只查询 `reviewDate = today`，不沿用昨天的评价。原因：昨天的评价不能代表今天的结果。

这与完成目标不同：

- 目标在缺少当天记录时可以展示“上次目标”；
- 评价在缺少当天记录时必须展示“尚未评价”；
- 绝不能把过去评价投影成今日评价。

### 14.2 保存时生成目标快照

```js
const exactGoal = getCompletionGoalForDate(item, reviewDate);
const goalContentSnapshot = exactGoal?.content || null;
```

编辑已有评价时：

```js
const dateChanged = originalReview.reviewDate !== reviewDate;

const snapshot = dateChanged
  ? getCompletionGoalForDate(item, reviewDate)?.content || null
  : originalReview.goalContentSnapshot;
```

### 14.3 状态文案映射

```js
const COMPLETION_REVIEW_RESULTS = {
  achieved: { label: '已达成', className: 'is-achieved' },
  partial: { label: '部分达成', className: 'is-partial' },
  missed: { label: '未达成', className: 'is-missed' },
};
```

未知数据库值不得静默显示为空，应回退为“未知结果”并在控制台记录异常。

## 15. 关键业务规则

1. 父任务和子任务均能拥有每日评价历史。
2. 每个任务每个日期最多一条评价。
3. 同日再次保存是更新，不生成第二条记录。
4. 评价结果和实际完成情况都必须填写。
5. 允许没有完成目标的日期填写评价。
6. 评价保存当时的目标文字快照。
7. 修改或删除目标不自动修改旧评价快照。
8. 不能评价未来日期。
9. 今日卡片只显示今日评价，不显示或沿用过去评价。
10. 明日视图不展示评价入口。
11. 普通分组不平铺评价正文，只提供入口和轻量状态。
12. 任务勾选不自动创建或修改评价。
13. 子任务完成情况不自动计算父任务评价。
14. 更改 `planned_date` 不删除、迁移或改写评价日期。
15. 删除评价不影响目标、任务和完成状态。
16. 删除任务通过外键级联删除评价历史。
17. 评价不参与顶部完成率、任务计数、排序和子任务进度。

## 16. 边界情况

### 16.1 当天没有完成目标

- 允许评价。
- 目标对照区显示“当天未设完成目标”。
- `goal_content_snapshot = NULL`。
- 历史中标记“无目标记录”，而不是隐藏目标区。

### 16.2 评价后修改当天目标

- 卡片继续展示最新目标。
- 评价保留保存时的目标快照。
- 历史详情可以看出计划后来发生过变化。
- 第一版不做“目标已变化”的自动差异提示。

### 16.3 评价后删除当天目标

- 评价仍然存在。
- 目标快照仍然存在。
- 不级联删除评价。

### 16.4 同日评价多次修改

- 保留一条评价。
- 更新 `result`、`content` 和 `updated_at`。
- 不记录逐次修改历史。

### 16.5 修改评价日期产生冲突

- 提示“该日期已有完成评价”。
- 用户可以取消或明确替换。
- 替换时更新目标日期已有记录，并删除原记录，避免违反唯一约束。

### 16.6 任务在评价当天不再安排于该日

- 仍允许通过历史面板编辑该日期评价。
- 评价归属于任务和日期，不要求 `planned_date` 永远等于评价日期。

### 16.7 很长的评价文字

- 数据库上限 500 字符。
- 卡片最多显示两行。
- dialog 展示全文。
- 移动端不允许横向滚动。

### 16.8 跨时区

- `review_date` 使用数据库 `date`，不存时区。
- 日期含义按用户本地日历日处理。
- `created_at` 和 `updated_at` 使用 `timestamptz`。

## 17. 可访问性

- 评价卡片使用 `<button>`，不能只给 `<div>` 绑定点击。
- 无障碍名称包含任务名和日期，例如“评价完成移动端重构的今日完成情况”。
- 达成结果使用真实 radio inputs 和 `<fieldset>` / `<legend>`。
- 结果不能只靠颜色表达，必须显示文字。
- 日期输入有可见标签并限制最大日期。
- 历史折叠按钮使用 `aria-expanded` 和 `aria-controls`。
- dialog 打开后，新增评价聚焦结果选择；编辑评价聚焦实际完成情况。
- dialog 关闭后，焦点返回触发按钮；列表重绘导致按钮失效时，返回同任务的新评价入口。
- 删除评价前确认具体日期。
- 错误与保存状态通过 `role="status"` 或 `aria-live` 告知。

## 18. 视觉方案

### 18.1 设计方向

本功能服务于个人日终复盘，页面的单一工作是让用户快速对照“计划”和“实际”。不重新设计整个工作台，继续使用当前项目的：

- 深色/多主题 token；
- `Inter` 与当前 display / utility 字体变量；
- 紧凑任务卡片；
- 细线、弱底色和小型状态标签；
- 今日橙、明日蓝、完成绿、危险粉红。

### 18.2 结构签名：对照账页

现有完成目标使用一条短竖线表示“当天承诺”。评价使用与它相邻但不同的“结果印记”：

```text
│ 今日完成目标
│ 计划文字

✓ 今日完成评价 · 部分达成
  实际结果文字
```

目标是计划线，评价是结果印记。这一组结构表达真实信息，而不是纯装饰。

### 18.3 克制原则

- 不增加新的主色。
- 不增加评分环、星级或进度条。
- 不同时使用粗边框、渐变、阴影和大图标强调评价。
- 卡片只有目标和评价两层，不再附加第三层“总结”。
- 评价缺失入口保持安静，已有结果才使用状态色。

## 20. 验收标准

### 20.1 数据

- 父任务和子任务都能保存评价。
- 同一任务同一日期不能产生两条评价。
- 删除任务会删除关联评价。
- 删除目标不会删除评价。
- 评价保留目标快照。
- 不同账号之间评价数据隔离。

### 20.2 今日显示

- 今日卡片在目标下方显示今日评价或评价入口。
- 三种结果的文字和视觉状态正确。
- 正文最多两行。
- 昨天的评价不会被显示为今日评价。
- 明日卡片不出现评价入口。

### 20.3 交互

- 可以新增、编辑和删除评价。
- 可以补录往日评价。
- 不能保存未来日期评价。
- 结果和实际完成情况缺失时不能保存。
- 日期冲突必须得到明确确认。
- 历史默认折叠。
- 关闭 dialog 后焦点返回正确。

### 20.4 非回归

- 评价不影响任务勾选状态。
- 评价不影响完成率和任务数量。
- 评价不影响子任务进度。
- 目标创建、编辑、历史和日期顺延功能保持不变。
- 父任务和子任务拖拽、分组、描述编辑保持不变。
- Realtime 的 todo、category 和 completion goal 频道保持正常。

## 21. 第一版明确不做

- 自动根据任务勾选推断评价结果；
- 自动把未评价视为未达成；
- 数字评分或百分比；
- 情绪、精力和工时字段；
- 评论、附件和多人评价；
- 每日自动弹窗；
- 浏览器后台通知；
- 今日所有任务的批量复盘流程；
- 自动从子任务评价汇总父任务评价；
- 目标与实际文字的 AI 对比或自动评分；
- 评价正文的逐次编辑版本历史。
